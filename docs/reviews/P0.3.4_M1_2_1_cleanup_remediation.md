# P0.3.4-M1.2.1 — Deterministic per-run cleanup remediation

Remediação (não auditoria) do finding **W4R-M12R-01 — MEDIUM — OPEN**, registado em
[P0.3.4_M1_2_commit_authorization_audit.md](P0.3.4_M1_2_commit_authorization_audit.md).
Escopo estrito: lifecycle do harness, fecho de conexões, supervisão de workers, cleanup
de databases descartáveis, cleanup de barriers/files/processos, diagnóstico de
bloqueadores de `DROP DATABASE`. **Nenhum código de produção foi alterado** —
`EvangelismService`, `DomainClock`, `track`/`step`/`progress`, `CheckinService`,
`ChildrenService`, migrations e schema de negócio permanecem intocados; nenhuma
migration foi criada. Wave 5 não foi iniciada.

## Root cause

Reproduzido ao vivo (não apenas inferido) num lote de execuções concorrentes reais
contra o `WaveThreeCheckinConcurrencyTest` completo: imediatamente após o processo
PHPUnit de uma corrida ter terminado (confirmado por `subprocess.communicate()` do
harness Python), uma thread do MySQL (`SHOW PROCESSLIST`) mostrava:

```
id=22951  command=Query  time=40  state=waiting for handler commit
info=DROP DATABASE IF EXISTS `mepa_wave3_test_m121diag_896c33a2a3844a5b9b21fdbd`
```

com **zero sessões** referenciando essa schema por `db=<schema>` no mesmo instante.
`performance_schema.metadata_locks` para essa schema mostrava dezenas de locks
`EXCLUSIVE`/`GRANTED` pertencentes à própria transação do `DROP DATABASE` (esperado —
é assim que o atomic DDL do MySQL 8 remove tabela a tabela) e, criticamente, uma
lock `SHARED`/`PENDING` de uma thread separada (id 37) contra `role_permissions`
dentro dessa mesma schema — uma referência a essa schema que **não aparece** ao
filtrar `information_schema.processlist` por `db = '<schema>'`, porque uma sessão
pode reter/pedir um metadata lock sobre objetos de uma schema sem ter essa schema
como o seu `db` corrente (ex.: acesso qualificado `schema.tabela`, ou uma sessão que
mudou de `db` depois de já ter adquirido o lock). Isto confirma exatamente a instrução
da secção 2 desta tarefa: `SHOW PROCESSLIST` sozinho sub-conta sessões relevantes;
`performance_schema.metadata_locks` é a fonte autoritativa.

Um controlo com zero carga concorrente (30 ciclos `CREATE`+`DROP DATABASE` vazios,
nenhuma ligação de aplicação) confirmou `DROP DATABASE` idle em 0.05s–0.4s sempre —
a lentidão **não é intrínseca ao DROP em si**, é condicional à carga concorrente do
host.

**Causa raiz:** `DROP DATABASE` sobre uma schema com ~127 tabelas, 255 FK e 81 CHECK
passa pelo atomic DDL do MySQL 8, cuja fase final de commit (`waiting for handler
commit`) partilha o pipeline de redo log / group commit do servidor com **todas** as
outras ligações — não apenas com sessões da própria schema. Quando uma corrida
irmã concorrente (o outro membro do par "parallel", ou o leg "child" de um ciclo
"loaded") está a committar muitas transações pequenas de worker ao mesmo tempo, essa
fase de commit do `DROP` serializa atrás dessa atividade e pode legitimamente demorar
dezenas de segundos — confirmado ao vivo a 40s ainda em curso, e confirmado a
completar sozinho pouco depois, **sem qualquer sessão bloqueadora identificável**.

**Achado operacional crítico, que explica directamente o sintoma original ("execuções
concluíram mas o DROP excedeu o prazo; as bases foram removidas depois"):** matar o
processo cliente (`mysql.exe`) que emitiu o `DROP DATABASE` **não pára o trabalho do
lado do servidor**. Confirmado directamente: um cliente Python que atingiu o seu
próprio timeout de 20s e foi terminado (`subprocess.TimeoutExpired` → kill) deixou o
`DROP DATABASE` a continuar a correr no servidor; instantes depois a schema já não
existia e `Threads_connected` tinha voltado a 1. Qualquer harness que mate o seu
cliente ao expirar um timeout e trate isso como falha, sem verificar a ausência real
da schema, vai reportar como `CLEANUP_FAIL` uma operação que, do lado do servidor, foi
um sucesso lento — exactamente o padrão documentado na auditoria independente.

Isto também significa que a higiene de conexões/sessões exigida pelas secções 4–7
desta tarefa é **necessária mas não suficiente** por si só: nas 90 corridas da
qualificação completa abaixo, `blocking_sessions_seen` ficou vazio em 90/90 — não
havia nenhuma sessão órfã para matar. A causa da lentidão observada nesta bateria foi
inteiramente o trabalho genuíno de `DROP` sob carga, não uma fuga de conexão. A
correcção tem por isso dois pilares: (1) a higiene de sessões/conexões exigida pela
tarefa, implementada de qualquer forma como defesa em profundidade e comprovada pelos
cenários B/D abaixo; e (2) tratar o cleanup como uma máquina de estados **verificada
por polling de ausência real**, nunca por timeout-e-kill do cliente.

## Lifecycle por run (implementado)

`scripts/wave4-m121/cleanup.py` implementa exactamente a ordem da secção 3:

```
DOMAIN TEST FINISHED (processo PHPUnit já reaped pelo chamador)
  → CONNECTIONS_DRAINED   (drain_connections: processlist.db= UNION metadata_locks
                            JOIN threads JOIN processlist, kill dos que sobrarem)
  → DATABASE_DROPPED      (drop_database_verified: DROP + poll de ausência real,
                            nunca kill-e-assume-falha do cliente)
  → FILES_REMOVED         (verificado; a remoção primária dos barriers do worker
                            já acontece em WaveFourWorkerHarness::close(), intocado)
  → CLEANUP_VERIFIED → DONE
   ou, em falha real:
  → CLEANUP_FAILED → RESCUE_CLEANUP → RESCUE_VERIFIED (cleanup_result permanece
                            CLEANUP_FAIL mesmo que o rescue tenha sucesso — secção 9/11)
```

Cada `RunTelemetry` grava (secção 14): `run_id`, `schema`, `domain_result`,
`domain_exit`, `domain_finished_at`, `connections_zero_at`, `drop_started_at`,
`drop_finished_at`, `files_removed_at`, `cleanup_verified_at`,
`cleanup_duration_ms`, `drop_attempts`, `blocking_sessions_seen`,
`metadata_locks_seen`, `cleanup_result`, `rescue_used`, `diagnostics` — sem PII (só
thread id/user/host/command/time/state do MySQL).

### Fecho de conexões (secções 4–7)

`referencing_sessions(schema)` une `processlist.db = schema` com
`metadata_locks JOIN threads JOIN processlist` (o sinal mais amplo, motivado pela
lacuna encontrada na investigação da causa raiz). Qualquer sessão devolvida é, por
construção, órfã deste run: a schema é gerada pelo harness com 24 hex aleatórios
(`secrets.token_hex(12)`), nunca aceite de fonte externa, e o processo PHP dono já foi
confirmado terminado antes deste passo correr — logo nunca pode ser `laravel`,
phpMyAdmin, ou outro run. `kill_orphan_sessions()` emite `KILL <id>` só sobre essas
linhas, nunca por heurística de host/user.

### DROP DATABASE verificado (secção 8) e guarda "laravel" (hard denied)

`guard_schema()` corre antes de qualquer SQL ser construído: recusa
`laravel`/`mysql`/`information_schema`/`performance_schema`/`sys` explicitamente, e
separadamente exige o padrão
`^mepa_(wave1|wave2|wave2f|wave2m1|m1audit|m1safety|wave3|wave4)_test_m121_[0-9a-f]{24}$`
— o mesmo prefixo que cada bootstrap PHP (`WaveThreeCase`, `WaveFourCase`,
`WaveOnePhysicalTest`, …) já exige do seu lado, mais o sufixo `_m121_` exclusivo desta
remediação. Nenhum nome chega de fora do processo. Testado no cenário H.

### Dois prazos distintos (secção 10)

`FUNCTIONAL_TEST_TIMEOUT_SECONDS = 300` (inalterado, aplica-se só ao processo
PHPUnit) e `CLEANUP_TIMEOUT_SECONDS = 150` (novo, só para o `DROP` + verificação),
nunca partilhados. O valor de 150s foi calibrado pela evidência recolhida nesta
remediação, não escolhido para "fazer passar":

| Condição | Amostras | p50 | p95 | p99 / max |
|---|---:|---:|---:|---:|
| Idle, zero carga concorrente | 30 | 0.06s | 0.08s | 0.41s |
| Reprodução ao vivo (root cause) | 1 evento | — | — | ≥40s em curso, absent momentos depois |
| Qualificação completa (90 runs: 50 isolated + 20 parallel + 20 loaded) | 90 | 2.97s | 26.66s | 75.38s |

`CLEANUP_TIMEOUT_SECONDS=150` fica confortavelmente acima do p99 observado (75.4s)
sem ser arbitrariamente longo. Em nenhuma das 90 corridas o `drop_attempts` excedeu 1
(o `DROP` sempre terminou dentro do seu próprio tempo, por mais lento que fosse); o
retry só foi exercitado deliberadamente pelos testes unitários E/E2.

### Retry (secção 9) e rescue (secção 11)

O retry é limitado a `CLEANUP_TIMEOUT_SECONDS` no total (nunca reemite `DROP` sobre
uma tentativa ainda em curso — poll de ausência primeiro, nova tentativa só depois).
Se o orçamento esgotar, o run fica **CLEANUP_FAIL** para sempre — `rescue_cleanup()`
(até 90s adicionais, mata sessões residuais + novo `DROP IF EXISTS` + poll) só existe
para não deixar lixo, nunca para converter o resultado em PASS. Provado
deterministicamente no teste `INTENTIONAL` (ver abaixo).

## Teste de falha intencional (secção 19) — detalhe

Ver cenário `INTENTIONAL` acima. Não foi possível reproduzir uma falha determinística
segurando uma sessão bloqueadora comum (`LOCK`/`SLEEP`), porque `drain_connections`
resolve esse caso correctamente em <1s (é exactamente o comportamento desejado —
provado pelo cenário E). A falha real reproduzida na causa raiz não tem nenhuma
sessão para matar (é trabalho interno do InnoDB), pelo que o teste força
deterministicamente o mesmo desfecho observável (`schema_exists` a reportar "ainda
presente" além do orçamento) sem depender de reproduzir a janela de tempo exacta de
~100s sob carga real. Confirmado: run fica `CLEANUP_FAIL`, `rescue_used=True`, e o
resultado nunca é convertido em `PASS` — o harness não maquilha resultados.
