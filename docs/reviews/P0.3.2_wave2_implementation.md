# P0.3.2 — Wave 2 Physical Implementation Report

**Author:** Claude (Sonnet 5), acting as implementer at the user's explicit instruction, after
confirming Wave 2 did not exist anywhere in the repository (no migrations, no report, no
evidence directory, no other branch/stash/worktree). The user selected "I'll implement Wave 2
now" from three offered options, explicitly accepting that the audit that follows is
**self-authored, not independent**. See `P0.3.2_wave2_gate.md` for the disclosed caveat.

## Scope

Wave 2 = the 43 tables assigned `wave: 2` in `docs/database/physical/migration_waves.json`:
Membership, Número Único, Legado (mapeamento de números legados), Transferências, Ministério
(classes/atribuições), Departamentos (categorias/definições/instâncias/postos/nomeações), Papéis
e Permissões, Fluxos de trabalho, Dispositivos/Sessões, Importação, and the adaptation of the
Laravel scaffolding `users` table to its approved shape. Plus the materialization of **W1-F01**
(`files.owner_department_id → department_instances.id`), deferred from Wave 1 because its target
table did not exist yet.

## What was built

- `scripts/lib/wave2-catalog.cjs` — Wave 2 catalog module (table list, dependency-ordered
  topological sort, per-table CHECK constraints following the same D-11 discipline as Wave 1:
  only fixed enums the dictionary's own description text states explicitly; everything else left
  as unconstrained `VARCHAR`, D-11-pending).
- `scripts/generate-wave2-migrations.cjs` — generator; produced 44 Laravel migration files
  (`apps/api/database/migrations/2026_09_13_0000{01..44}_*.php`): 42 `CREATE TABLE` migrations,
  one migration that materializes W1-F01, and one migration that `ALTER`s (never drops/recreates)
  the scaffolding `users` table into its approved shape.
- `apps/api/app/Domain/Membership/MemberNumberGenerator.php` — the MEPAAAMMSSSSSS Número Único
  allocator: locks the `memberships` row (`FOR UPDATE`), requires `approved_at IS NOT NULL`,
  replays the existing number if one is already allocated (idempotent), locks the
  `member_number_sequences` singleton row, increments a continuous national counter that never
  resets on month/year boundaries, and writes both `member_numbers` and the advanced sequence
  inside one transaction.
- `scripts/inspect-wave2-schema.php` + `scripts/validate-wave2-schema.cjs` — an
  information_schema-based validator for the Wave1∪Wave2 union (74 catalog-tracked tables),
  supporting both a physical (real MySQL) mode and a static (migration-capture-only) mode,
  mirroring the Wave 1 validator's shape but extended to check W1-F01's materialization and a
  repo-wide CASCADE audit.
- `scripts/wave2-concurrency-worker.php` — a standalone worker process (spawned via `proc_open`)
  used by the concurrency test to prove genuine multi-process safety, not simulated interleaving.
- `apps/api/tests/Database/WaveTwoPhysicalTest.php` (12 tests / 232 assertions) and
  `WaveTwoConcurrencyTest.php` (4 tests / 59 assertions).

## Execution evidence

All of it is real, run against a disposable Docker `mysql:8.4` container (`mepa-wave2-mysql`,
port 33092) never touching any other project's containers. See
`docs/database/physical/wave2_test_summary.json` for the full PASS/FAIL/SKIP ledger and
`wave2_physical_validation.json` / `wave2_static_validation.json` for the raw validator output.

- Fresh path: `php artisan migrate` ran all 79 migrations (4 scaffolding + 31 Wave 1 + 44 Wave 2)
  against a virgin database in one pass — 100% success.
- Upgrade path: Wave 1 migrated first (batch 1), then Wave 2 (batch 2); Wave 2 then rolled back
  and re-migrated inside `WaveTwoPhysicalTest::test_migrate_rollback_and_remigrate` — Wave 1's 31
  tables, `users`' scaffolding shape, and the absence of the W1-F01 FK were all correctly restored
  after rollback, then correctly re-applied on remigration.
- `validate-wave2-schema.cjs` (information_schema mode): 74 tables, 629 columns, 131 foreign
  keys, 57 checks, **0 CASCADE**, **0 drift**, W1-F01 verified `MATERIALIZED` with
  `RESTRICT`/`RESTRICT`.
- Concurrency: real `proc_open` worker processes racing `MemberNumberGenerator::generateFor()` at
  batch sizes 2, 10, and 30 — zero duplicate numbers/sequence values, contiguous allocation, and a
  dedicated same-membership race test proving serialization (exactly one row, sequence advances by
  exactly one, both callers get the identical number). Separate single-process tests proved
  idempotent replay, rollback safety (an aborted transaction leaves no row and does not advance
  the sequence), month-boundary continuity (`MEPA2609000146 → MEPA2610000147`), year-boundary
  continuity (`→ MEPA2701000148`), and sequence exhaustion at 999999.

## Known imperfections (carried into the audit as findings, not silently fixed)

1. The `users`-adaptation migration's `down()` re-adds the scaffolding columns without `AFTER`
   clauses, so a full rollback leaves a slightly different column order than Laravel's pristine
   default (functionally identical, cosmetic only).
2. `ministerial_class_periods` has no DB-level guarantee against two open (unclosed) periods for
   the same person — confirmed APPLICATION_ENFORCED, same discipline as Wave 1's five tracked
   skips, not yet built.
3. A stale, unrelated leftover chunk file from an earlier interrupted Graphify session
   (`docs/reviews/P0.2_*`-era content) was found in `graphify-out/` predating this work; merging
   it caused a benign but unrelated node-count shrink via duplicate-concept consolidation. It was
   excluded from this update and left on disk renamed
   `.graphify_chunk_wave1_docs.json.stale-unrelated-set-aside` for visibility rather than deleted.
