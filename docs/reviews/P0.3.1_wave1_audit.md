## 2. Mecanismo de constraints diferidas — avaliação

**Já existe um mecanismo funcional**, não apenas uma nota em prosa. Confirmei por leitura de `scripts/lib/wave1-catalog.cjs`:

```js
const deferred = [{ table: 'files', column: 'owner_department_id', target: 'department_instances.id', wave: 2, reason: '...' }];
```

O validador usa este array para produzir **dois modelos distintos** do schema esperado: um "estrito" (inclui a FK, por omissão) e um "staged"/`--allow-deferred` (exclui-a explicitamente). Confirmei em execução real:

| Modo | `errors` | `strict_errors` | `deferred_foreign_keys` no relatório | Exit code |
|---|---|---|---|---|
| Estrito (omissão) | 1 (a FK ausente, com `path`, `expected`, `actual:"missing"`) | 1 | Sempre presente | 1 |
| `--allow-deferred` | 0 | **1 (preservado)** | Sempre presente | 0 |

Isto satisfaz exactamente o requisito "o validador estrito deve diferenciar MISSING_UNEXPECTED de DEFERRED_APPROVED... nunca simplesmente deixar de validar a FK": mesmo em modo relaxado, a ausência da FK nunca desaparece do relatório — fica sempre visível em `strict_errors` e cruzável com `deferred_foreign_keys`.

**O que falta para a forma formal pedida:** o array `deferred` não tem `id` explícito (ex.: `"W1-F01"` só existe em texto de `reason`, nunca como campo estruturado), não separa `target_table`/`target_column` (usa uma string combinada `"department_instances.id"`), não tem `status` (PLANNED/DEFERRED_APPROVED/MATERIALIZED/CANCELLED — hoje é binário: está no array ou não está), não tem `origin_wave` explícito nem `enforcement_until_materialized`.

**Recomendação (não bloqueante):** antes da Wave 2 introduzir um segundo caso de FK diferida, formalizar isto num ficheiro dedicado (`docs/database/physical/deferred_constraints.json`) com os dez campos pedidos, e fazer o validador ler dele em vez de um array fixo no código. Com um único caso hoje, o mecanismo actual já cumpre a função; não escalará de forma legível para vários casos simultâneos nas Waves seguintes.

## 14. Findings

### F-W1-01 — Corrupção de codificação em relatórios da Wave 1

- **Severidade:** LOW
- **Área:** Documentação
- **Migration/Tabela:** N/A — afecta `docs/reviews/P0.3.1_wave1_implementation.md`, `docs/database/physical/P0.3.1_wave1_report.md`, `docs/database/physical/wave1_schema_report.md`, `docs/database/physical/wave1_graphify_report.md` (caracteres acentuados substituídos por `?` literal, ficheiro é ASCII puro, confirmado por `file`); `docs/database/physical/README.md` tem um defeito diferente (UTF-8 duplamente codificado, produzindo mojibake do tipo `Ã§Ã£o`).
- **Problema:** perda irreversível de acentuação portuguesa nos primeiros quatro ficheiros (bytes `0x3F` literais onde deveriam estar `ã`, `ç`, `õ`, etc.); no quinto, os bytes são UTF-8 válido mas semanticamente errado (dupla codificação).
- **Evidência:** `file docs/database/physical/P0.3.1_wave1_report.md` → "ASCII text"; dump hexadecimal confirma `0x3f` nas posições esperadas de acentos; `file docs/database/physical/README.md` → "UTF-8 text" mas o conteúdo lido mostra "FundaÃ§Ã£o" em vez de "Fundação".
- **Impacto:** apenas legibilidade/profissionalismo dos relatórios; **confirmei que não afecta nenhuma migration, schema, teste ou validador** (todos os ficheiros `.php`/`.sql`/`.json` relevantes são ASCII puro por design, sem necessidade de acentuação).
- **Recomendação:** regenerar os quatro relatórios ASCII-corrompidos e o README com codificação UTF-8 correcta (o defeito é consistente com escrita através de um terminal com codepage Windows incorrecto); considerar adicionar uma verificação de `file`/codificação ao validador documental para apanhar regressões futuras.
- **Bloqueia Wave 2?** NÃO

### F-W1-02 — Mecanismo de constraints diferidas funcional mas não formalizado

- **Severidade:** LOW
- **Área:** Migration quality / validador físico

### F-W1-03 — Os cinco skips de aplicação não têm wave/fase/responsável atribuído

- **Severidade:** LOW/MEDIUM
