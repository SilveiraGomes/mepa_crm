## 3. Vocabulário académico (Secção 8 da missão)

| Termo | Definição operacional neste desenho | Tabela |
|---|---|---|
| **Unidade Académica** | Um "motor" institucional (EBD, IBT, Formação de Quadros/RH), ancorado a um nível da árvore organizacional. É o nível mais alto — não é polo. | `academic_units` |
| **Programa** | Um percurso formativo oferecido por uma Unidade Académica (ex.: "Bacharelato Teológico IBT"). | `programs` |
| **Currículo (versão)** | Um conjunto **versionado e imutável após publicação** de cursos exigidos/opcionais de um Programa. Uma alteração curricular gera nova versão; a antiga permanece intacta para quem já a cursou. | `curricula` (UNIQUE `program_id,version`) |
| **Curso** | Unidade de conteúdo reutilizável **entre currículos e entre programas** (ex.: "Hermenêutica" pode aparecer no currículo do IBT e num curso intensivo pastoral). É o mesmo `courses` já criado na Wave 4 para Discipulado — reutilização deliberada, ver Secção 4. | `courses` (Wave 4, já física) |
| **Versão do curso** | Conteúdo congelado por versão (ementa, política de conclusão). Uma `class` ancora-se a uma versão específica, nunca ao curso "vivo". | `course_versions` (UNIQUE `course_id,version`) |
| **Módulo** | Subdivisão sequencial de uma versão de curso. | `course_modules` |
| **Aula (lesson)** | Unidade de conteúdo dentro de um módulo — **distinta de uma sessão lectiva concreta de turma**. | `lessons` |
| **Recurso** | Metadado de vídeo externo (YouTube/Vimeo, conforme §14.3 do baseline) ou material privado via `files`. | `resources`, `lesson_resources` |
| **Coorte (cohort)** | Agrupamento de turmas dentro de um programa/currículo (ex.: "Turma de Ingresso 2027"). | `cohorts` |
| **Turma (class)** | A **oferta concreta** de uma versão de curso: ano, professor(es), capacidade, opcionalmente numa coorte. É aqui — não no `course` — que "quando e quem" vive (Secção 20 da missão). | `classes` |
| **Sessão lectiva** | Ocorrência concreta de aula de uma turma (data/hora), opcionalmente ancorada a `event_sessions`. | `class_sessions` |
| **Professor/Formador** | Papel académico de uma Person, sem exigir membership. | `instructors`, `class_instructors` |
| **Aluno** | Não é uma tabela de identidade — é a Person referenciada por `enrollments.person_id`. | (papel, não tabela) |
| **Matrícula (enrollment)** | Relação Person↔Turma. | `enrollments` (UNIQUE `person_id,class_id`) |
| **Frequência/Presença** | Registo por matrícula e sessão. | `academic_attendance` |
| **Avaliação (assessment)** | Definição de instrumento de avaliação de uma versão de curso, com limites aprovados (nota máxima, nota de aprovação, tentativas, peso). | `assessments` |
| **Tentativa** | Ocorrência numerada de uma avaliação por matrícula. | `assessment_attempts` |
| **Nota (grade)** | Resultado versionado e homologado por tentativa — nunca sobrescrito, apenas nova versão. | `grades` |
| **Progresso** | Cache derivada e reproduzível (não é diploma). | `progress`, `resource_progress` |
| **Certificado** | Documento versionado emitido após homologação; revogação preservada, nunca apagada. | `certificates` |
| **Histórico académico (transcript)** | Documento oficial congelado por Pessoa+Currículo+versão. | `transcripts`, `transcript_lines` |

Esta terminologia evita as duplicações semânticas que a missão pede para prevenir (Secção 8): `program ≠ course` (programa agrega currículo, que agrega cursos); `course ≠ class` (curso é catálogo reutilizável, turma é oferta concreta); `class ≠ lesson/session` (turma é o continente; aula é conteúdo; sessão é ocorrência agendada).

## 4. Estrutura académica única para EBD / IBT / Formação de Quadros (Secções 9, 13–15)

O mesmo motor (`academic_units → programs → curricula → courses/course_versions → classes → enrollments → assessments/grades → certificates`) atende aos três programas sem tabelas paralelas:

- **EBD** — pode usar um `program` sem `curricula` versionadas rigidamente por semestre; `assessments` são opcionais (a missão pede avaliação qualitativa/presença obrigatória — suportado porque `assessments` não é obrigatória por `class`, e `progress`/`academic_attendance` sozinhas podem sustentar uma "conclusão" simples via `course_versions.completion_policy_metadata` JSON, que já existe no catálogo precisamente para parametrizar isto sem novo schema).
- **IBT** — usa a via completa: `programs → curricula (por ano/semestre) → curriculum_courses (ordem+obrigatoriedade) → course_prerequisites → classes → assessments com pesos/tentativas → grades → transcripts`.
- **Formação de Quadros / cursos pastorais** (Secção 15: História da MEPA, PAT, PNT, Hermenêutica, TICs, etc.) — cada módulo do intensivo pastoral é um `course` reutilizável (o mesmo catálogo de `courses` usado por Discipulado na Wave 4), agrupado numa `class`/`cohort` de curta duração, sem exigir estrutura semestral.

**Confirmação:** não existem, nem são propostas, `ebd_students`, `ibt_students`, `training_students`, `academic_guardians` ou qualquer outra tabela de identidade paralela.

## 5. Instituição / Polo académico (Secção 10) — GAP identificado

`academic_units` tem exactamente: `id, unit_id(FK organizational_units), code, name, status, created_at, lock_version`. É uma tabela **plana**, sem auto-hierarquia (`parent_id`). Isto modela bem o nível de "instituição" (EBD nacional, IBT nacional), ancorado a **um único** `organizational_units.id`.

**O catálogo actual não tem uma entidade "Polo" distinta.** `classes` tem `academic_unit_id` e `course_version_id`, mas **nenhuma coluna de unidade organizacional ou localização física própria** — a única via indirecta de localização é opcional: `classes → class_sessions.event_session_id → event_sessions → event_locations`.

Isto significa que, tal como desenhado hoje, **"IBT Polo Huambo" não é directamente representável nem consultável** sem forçar todas as sessões da turma a passar por `event_sessions` (o que nem sempre fará sentido — uma turma pode não precisar de check-in tipo evento).

**Recomendação (proposta, não aprovada — ver ADR-0015 em anexo):** adicionar duas colunas nullable a `classes` — `unit_id BIGINT UNSIGNED NULL FK→organizational_units` (RESTRICT) e `location_id BIGINT UNSIGNED NULL FK→physical_locations` (RESTRICT) — para que uma turma possa declarar directamente "onde" funciona (o polo/unidade responsável), sem depender de `event_sessions`. Isto seria uma alteração aditiva a uma tabela ainda não fisicamente criada (Wave 5 não implementada), logo **não** viola a Secção 3 da missão (não mexe em migrations aprovadas de Waves 1–4). Alternativa sem alteração de schema: aceitar que o "polo" emerge apenas do `academic_unit_id` (se cada polo for modelado como o seu próprio `academic_units.unit_id`, ex.: uma linha "IBT Huambo" separada de "IBT Nacional") — mas isto multiplicaria linhas de `academic_units` por polo, o que a Secção 10 explicitamente não quer confundir com organizational_unit/congregação.

**Estado:** ~~DECISION REQUIRED~~ **RESOLVIDO em P0.3.5-A0.1** (`docs/reviews/P0.3.5_A0_1_academy_decision_gate.md`, Secção 8; `docs/adr/0015-academia-scope-and-location-proposals.md`, Decisão A — ACCEPTED). `classes.unit_id` foi REJECTED (redundante face a `academic_unit_id → academic_units.unit_id`). `classes.location_id` foi ACCEPTED como local por defeito da turma, com `class_sessions.event_session_id → event_locations` a prevalecer por sessão quando presente.

## 6. Aulas/Sessões — estratégia de presença (Secção 21)

**Decisão já reflectida no catálogo, aqui documentada e ratificada:** opção **B** da missão — "academic class session referencia event_session", com presença dedicada.

- `class_sessions.event_session_id` é **nullable**: uma sessão lectiva pode opcionalmente ancorar-se à infraestrutura genérica de eventos (reaproveitando `event_sessions`, `event_checkins`, credenciais, QR — ADR-0012) quando a turma quiser check-in com dispositivo/QR (ex.: uma aula pública do IBT com controlo de acesso).
- `academic_attendance` é **dedicada** (não é `event_attendance`), com `UNIQUE(enrollment_id, class_session_id)` — porque a semântica de frequência académica (percentual de frequência, faltas justificadas, mínimo de presença para aprovação — Secção 22) é diferente da semântica de "compareceu a um culto/evento" e teria de ser forçada de forma artificial em `event_attendance`, que não tem conceito de matrícula, curso ou aprovação.

**Por que não a Opção A pura (reutilizar só `event_attendance`):** `event_attendance` não referencia `enrollment_id`, `course_version_id` nem suporta estados como `JUSTIFIED`/`LATE` com significado académico; forçar isso exigiria alterar uma tabela aprovada da Wave 3, o que a Secção 3 proíbe.
**Por que não a Opção C pura (presença 100% nova, sem ligação a eventos):** perderia a reutilização de credenciais/QR/check-in já auditado no ADR-0012 para os casos em que a turma efectivamente quer esse mecanismo.

A escolha do catálogo é, portanto, a correcta e já está feita — este documento apenas a formaliza e explica o porquê, como a missão pede.

## 7. Avaliações, notas, progresso, certificados (Secções 23–28)

Separação já implementada no catálogo, exactamente como a missão exige:

```
assessments (definição: max_score, pass_score, max_attempts, weight — por course_version)
   → assessment_attempts (ocorrência: numerada por matrícula, UNIQUE(assessment_id, enrollment_id, attempt_number))
      → grades (resultado: UNIQUE(attempt_id, version) — nova versão em vez de sobrescrever; graded_by, reason, status)
```

- **Escala de nota:** `assessments.max_score`/`pass_score` são `DECIMAL(9,4)` livres — não presumem 0–20 nem 0–100; a escala é uma política por avaliação, não uma constante do sistema (Secção 24 satisfeita).
- **Auditabilidade:** `grades` nunca é UPDATE — cada correcção é uma nova linha com `version` incrementada, `graded_by`, `graded_at`, `reason`; o histórico completo de revisões fica preservado (Secção 25 satisfeita, e alinhado com o padrão de "versões publicadas imutáveis" do ADR-0008).
- **Progresso:** `progress` é uma **cache derivada e reproduzível** (`completion_ratio`, `source_version`) — explicitamente "não diploma por si só" na descrição do catálogo — e `resource_progress` guarda evidência de acesso a vídeo/material. Isto respeita a Secção 22 ("não guardar percentuais derivados salvo motivo de performance/auditoria documentado" — o motivo aqui é ambos: performance de consulta de histórico de 300 mil matrículas, e auditoria, já que `source_version` referencia a política usada no cálculo).
- **Certificados:** `certificates` é versionado (`UNIQUE(enrollment_id,version)`), tem `token_hash BINARY(32)` (nunca o `public_id` — reutiliza exactamente o padrão hash-only do ADR-0012/ADR-0009: "ULID não é segurança"), `revoked_at` preserva em vez de apagar, e `file_id` liga ao PDF real via `files`/reuso de storage (Secção 26/27 satisfeitas). **Emissão nunca é inferida da existência de uma linha** — `certificates.approved_by` (FK `users`, NOT NULL) obriga a um acto de homologação explícito, e a permissão de emitir (Secção 36) deve ser distinta de lançar nota (ver Secção 8 abaixo).
- **Histórico consolidado:** `transcripts` (`UNIQUE(person_id,curriculum_id,version)`) + `transcript_lines` dão a visão consolidada por Pessoa exigida na Secção 28, através de múltiplas matrículas/cursos/anos.

## 8. Scope, autorização e permission matrix (Secções 33–36)

### 8.1 Convenção de permissão (nova — catálogo `permissions`/`scopes` está vazio, sem seed ainda)

`permissions` tem colunas `code, action, data_type, maximum_classification` (não é uma string `"module.action"` livre). Proposta de convenção para Academia, coerente com a estrutura já existente e sem inventar um padrão alternativo:

| `code` | `action` | `data_type` | `maximum_classification` | Descrição |
|---|---|---|---|---|
| `ACADEMY_VIEW` | `VIEW` | `ACADEMIC_RECORD` | `Restrito` | Ver programas/turmas/matrículas |
| `ACADEMY_MANAGE` | `MANAGE` | `ACADEMIC_CATALOG` | `Restrito` | Gerir programas/currículos/cursos/turmas |
| `ACADEMY_ENROLL` | `CREATE` | `ENROLLMENT` | `Restrito` | Matricular/cancelar matrícula |
| `ACADEMY_TEACH` | `MANAGE` | `CLASS_INSTRUCTION` | `Restrito` | Atribuir/remover professor de turma |
| `ACADEMY_ATTENDANCE` | `RECORD` | `ATTENDANCE` | `Restrito` | Registar presença |
| `ACADEMY_ASSESS` | `RECORD` | `GRADE` | `Restrito` | Lançar/rever nota |
| `ACADEMY_GRADES_VIEW` | `VIEW` | `GRADE` | `Restrito` | Ver notas (aluno, encarregado quando menor) |
| `ACADEMY_CERTIFY` | `ISSUE` | `CERTIFICATE` | `Confidencial` | Emitir/revogar certificado — **distinto de `ACADEMY_ASSESS`** (Secção 36) |
| `ACADEMY_ADMIN` | `MANAGE` | `ACADEMY_CONFIG` | `Altamente sensível` | Configuração institucional (políticas, escalas) |

Estes nomes só se tornam definitivos após seed institucional aprovado (Secção 46 — não converter em seed definitivo sem aprovação do contrato correspondente); aqui são uma **proposta de contrato**, não um seed.

### 8.2 Scope territorial (Secção 34) — GAP identificado

`scopes` tem `unit_id, department_instance_id (nullable), include_descendants, scope_kind ∈ {UNIT, UNIT_DEPARTMENT}`. **Não existe um `scope_kind` para "âmbito académico"** (ex.: limitar `ACADEMY_ASSESS` a uma `class_id` ou `academic_unit_id` específica) — estender o enum `scope_kind` e adicionar uma coluna `academic_unit_id` nullable a `scopes` seria uma alteração aditiva à tabela `scopes` (Wave 2, já aprovada e fisicamente criada), o que **exigiria uma migration ALTER em Wave 5**, não uma reescrita da migration de Wave 2 original — compatível com o precedente já usado em `2026_09_13_000024_wave2_materialize_w1_f01_files_owner_department_id.php` (uma migration posterior que materializa uma FK adiada, sem tocar no ficheiro de migration original).

**Recomendação preferida (sem alterar `scopes`):** seguir o precedente do ADR-0012 (revalidação em transacção de commit, não apenas checagem de scope genérico) — a autorização fina de Academia (ex.: "este professor só altera notas da sua turma") verifica-se **ao nível do serviço**, consultando directamente `class_instructors` (existe uma linha activa `instructor_id ↔ class_id`?) e `enrollments` (a matrícula pertence a essa `class_id`?), em vez de depender de `scopes` para granularidade de turma. `scopes`/`user_role_scopes` continuam a resolver o nível institucional mais amplo (`ACADEMY_ADMIN` num `unit_id` com `include_descendants`), exactamente como já fazem para outros domínios. Isto satisfaz a Secção 33 (permission matrix) e a Secção 35 (professor não altera fora do scope) **sem exigir ALTER a uma tabela de Wave 2**, e é o desenho recomendado.

A alternativa (estender `scopes`) fica registada no ADR-0015 em anexo como opção B, não escolhida por defeito.

**Estado:** ~~GAP~~ **RESOLVIDO em P0.3.5-A0.1** (ADR-0015, Decisão B — ACCEPTED). Confirmado: sem novo `scope_kind`; matriz completa de autorização (institutional scope + class assignment + admin override, por permissão) publicada em `docs/reviews/P0.3.5_A0_1_academy_decision_gate.md`, Secção 9.

**Regra dura (Secção 34):** nenhum endpoint deve aceitar `unit_id`/`class_id` do cliente como fonte de autoridade — a autorização deriva sempre de `user_role_scopes` (nível institucional) + `class_instructors`/`enrollments` (nível de turma), nunca de parâmetro de query. Fail closed por defeito, tal como o resto do sistema.

## 9. Child safety — pontos de integração obrigatórios (Secção 37, teste crítico C7)

O catálogo Academia **não tem** FK directa para `child_profiles`. Isto está correcto architecturalmente (Academia não deve saber de segurança infantil no schema, tal como `event_attendance` também não sabe) — mas exige um contrato de serviço explícito, documentado aqui porque a missão pede exactamente isto ("documentar os pontos de integração", não necessariamente alterar o schema):

1. **Matrícula (`enrollments`):** antes de aprovar uma matrícula (`approved_by` preenchido), o serviço de matrícula deve verificar se `enrollments.person_id` tem uma linha em `child_profiles`. Se sim, a matrícula só avança com uma `guardian_authorizations` válida e não revogada (`authorization_kind` compatível, `status` activo, período `starts_at/ends_at` cobrindo a data) — reutilizando exactamente a mesma tabela e política usada em Wave 4, nunca uma cópia.
2. **Presença/Check-in (`academic_attendance`, e via `class_sessions.event_session_id` quando aplicável):** para uma Person com `child_profiles`, o check-in de entrada/saída de uma sessão presencial reutiliza o padrão `ChildParticipationSafetyGate`/`ChildrenService` já existente (`requireGenericParticipant()` bloqueia check-in genérico para quem tem `child_profiles` — Wave 4, W4R-01) — **nunca** um caminho de presença académica que ignore esse gate. Nenhuma "excepção académica" é criada.
3. **Consentimentos (`person_consents`):** se Academia recolher consentimento adicional específico (ex.: uso de imagem em certificado, gravação de aula), reutiliza `person_consents.purpose` com um novo valor de propósito (ex.: `ACADEMY_MEDIA_CONSENT`), nunca uma tabela de consentimento paralela.
4. **Faixa etária (`age_band_rules`, `department_transition_recommendations`):** transição de faixa etária continua a gerar apenas recomendação (Wave 4), nunca alteração automática — Academia não deve promover automaticamente um aluno de EBD infantil para EBD adulto só porque fez aniversário; a recomendação é o mesmo mecanismo existente.

Isto é registado como **REQUIRED AND PLANNED** (Secção 64) — não é um gap de tabela, é um contrato de serviço que a implementação de Wave 5 deve honrar desde o primeiro commit de serviço de matrícula/presença.

## 10. Concorrência e invariantes de base de dados (Secções 48, 54–56)

| Risco (Secção 48) | Invariante já no catálogo | Suficiente? |
|---|---|---|
| Dupla matrícula concorrente | `UNIQUE(enrollments.person_id, class_id)` | ✅ Sim — segunda tentativa falha na UNIQUE, converge deterministicamente |
| Dupla inscrição em avaliação | `UNIQUE(assessment_attempts.assessment_id, enrollment_id, attempt_number)` | ✅ Sim, desde que `attempt_number` seja atribuído em transacção com lock (ex.: `SELECT ... FOR UPDATE` sobre a última tentativa) — **contrato de serviço a documentar em API (Secção 11)**, a UNIQUE por si só previne duplicação mas não atribui o número — serviço deve calcular `MAX(attempt_number)+1` dentro da mesma transacção que insere |
| Lançamento concorrente de resultado | `UNIQUE(grades.attempt_id, version)` + `lock_version` optimista em `assessment_attempts` | ✅ Sim — nova versão nunca colide, e o serviço deve ler `lock_version` antes de decidir o próximo `version` |
| Finalização concorrente de resultado | `grades.status` + `lock_version` | ✅ Suficiente com verificação optimista no serviço (comparar `lock_version` no UPDATE) |
| Emissão duplicada de certificado | `UNIQUE(certificates.enrollment_id, version)` + `UNIQUE(token_hash)` | ✅ Sim — mesma matrícula não pode ter dois certificados da mesma versão; nova emissão é nova versão, nunca reescreve |
| Alteração curricular durante turma activa | `curricula.published_at` + imutabilidade após publicação; `classes.course_version_id` aponta para uma versão **congelada**, nunca para "o curso vivo" | ✅ Sim — uma nova versão de currículo/curso não afecta turmas já a decorrer, que continuam ancoradas à versão antiga |

**Nenhuma destas invariantes depende apenas de checagem em aplicação** (Secção 48: "não confiar apenas em application checks") — todas têm uma UNIQUE ou FK a fazer cumprir o invariante na base de dados, com a aplicação apenas a decidir "o quê" (ex.: o próximo número de tentativa) dentro de uma transacção.

### Idempotência (Secção 49)

Operações que justificam idempotência explícita, reutilizando `idempotency_requests` (já existente, usado desde Wave 3 para check-in):
- **`enroll`** — pedido repetido com a mesma chave de idempotência deve devolver a matrícula já criada, nunca duplicar (a UNIQUE já protege o dado; a idempotência protege a resposta ao cliente em caso de retry de rede).
- **`certificate issue`** — emissão é uma acção sensível e cara (gera PDF, `file_id`); idempotência evita gerar dois ficheiros para o mesmo pedido duplicado.
- **`bulk results import`** (se vier a existir, ex.: importação de notas de exame em lote) — cada linha do lote deve ser idempotente por `(assessment_id, enrollment_id, attempt_number)`.
Não se propõe idempotência para `attendance` unitária (o `UNIQUE(enrollment_id,class_session_id)` já a torna naturalmente idempotente sem necessidade de chave adicional) nem para leituras.

## 12. State machines (Secção 50) — PROPOSTAS, pendentes de D-11

D-11 ("estados exactos por tabela/transições") está **BLOCKED** institucionalmente. As máquinas de estado abaixo são propostas de trabalho para orientar o desenho de serviço e os testes; os valores literais de `status` (`VARCHAR(64)`) não são um enum fechado no schema (por desenho — D-11 pendente), mas devem ser validados por `CHECK`/serviço antes da primeira migration real, conforme já é o padrão noutras tabelas do sistema (ex.: `department_instances.status IN (...)`).

**Enrollment (`enrollments.status`):**
`PENDING → APPROVED → ACTIVE → COMPLETED`
`PENDING → REJECTED` (terminal)
`ACTIVE → SUSPENDED → ACTIVE | WITHDRAWN` (terminal)
`ACTIVE → WITHDRAWN` (terminal)
`ACTIVE → FAILED` (terminal, via finalização de resultado)
Transições `APPROVED`/`REJECTED` exigem `approved_by`; auditável via `audit_logs`.

**Turma/Oferta (`classes.status`):**
`DRAFT → PUBLISHED → IN_PROGRESS → CLOSED`
`PUBLISHED → CANCELLED` (terminal, antes de iniciar)
Matrículas só se criam com `classes.status IN (PUBLISHED, IN_PROGRESS)`.

**Avaliação/Tentativa (`assessment_attempts.status`):**
`STARTED → SUBMITTED → GRADED`
`STARTED → EXPIRED` (terminal, se ultrapassar prazo sem submissão)

**Resultado (`grades.status`):**
`DRAFT → HOMOLOGATED` (terminal por versão; correcção = nova linha com `version+1`, nunca reabre a anterior)

**Certificado (`certificates.status`):**
`ISSUED → REVOKED` (terminal; `revoked_at` preenchido, linha nunca apagada)

Todas as transições fora desta lista são proibidas por defeito (fail closed) e devem ser auditadas em `audit_logs` com `actor_id`, `before_metadata`/`after_metadata`, `reason`.

**Database invariants:** RESTRICT universal, versionamento imutável em `curricula`/`course_versions`/`grades`/`certificates`, `public_id` só nas 9 tabelas com exposição externa.

**Attendance strategy:** Opção B — `academic_attendance` dedicada + `class_sessions.event_session_id` opcional.
**Event reuse decision:** parcial e opcional, justificada na Secção 6.

**API contracts:** 10 operações desenhadas (Secção 11), sem implementação.

**Sensitive data:** `Restrito` por defeito; `Confidencial`/`Altamente sensível` propostos para certificação/admin; `R-MENOR` prevalece sobre `R-ACADEMIA` quando aplicável.

**Seeds strategy:** nenhum seed definitivo nesta fase; classificação REFERENCE/DEVELOPMENT/TEST definida (Secção 15).

**Test Infrastructure V2:** aplicável, `scripts/wave4-m121/` não deve ser evoluído; nova suite estende via V2.
**Critical tests:** C1–C10 mapeados a invariantes de schema concretas (Secção 16).

**D-02–D-12:** preservadas sem alteração; **D-09 é bloqueio directo e nomeado para migrations de Academia** (não para este desenho).

**Graphify:** consultado, coerente, sem identidade paralela detectada, sem necessidade de reconstrução nesta fase.
