## Desenho da fronteira

Cada writer inicia uma transacção, executa validação provisional, adquire os locks e realiza a escrita de negócio e o audit de sucesso. A autorização decisiva usa `DomainAccess::authorizeMany()`: adquire sob shared lock sessão, actor, concessões, scopes, roles e todas as permissões, e então amostra uma única vez `DomainClock::now($db)` (`UTC_TIMESTAMP(6)`). Todas as permissões e condições temporais são avaliadas nesse mesmo instante, sem mais SQL antes do commit. O último check de todas as permissões requeridas ocorre após qualquer insert, lookup, FK/unique wait e audit insert, imediatamente antes de devolver o callback para o commit da transacção Laravel. Falha de autorização lança `ACTOR_NOT_AUTHORIZED` e provoca rollback de negócio e audit. Não há email, SMS, webhook, dispatch de queue, write de filesystem ou notificação externa no caminho de escrita do `EvangelismService` ou `DomainAccess`.

| Writer | Permissões | Transaction start / clock provisional | Locks e possíveis waits | Writes | Clock decisivo / commit authorization / commit |
|---|---|---|---|---|---|
| campaign | OUTREACH_WRITE | `run()`; DB clock antes do trabalho | event shared lock, FK/unique/insert, audit FK | campanha + audit | `run():commitAuthorize()` após audit; commit |
| contact | OUTREACH_WRITE | `run()`; DB clock antes do trabalho | campaign, Pessoa exclusive/shared, status, duplicate lookup, insert, audit | contacto + audit ou id existente | `run():commitAuthorize()` após último SQL; commit |
| followup | OUTREACH_WRITE | `run()`; DB clock antes do trabalho | contact/campaign, performer/status, insert, audit | followup + audit | `run():commitAuthorize()` após audit; commit |
| decision | OUTREACH_WRITE | `run()`; DB clock antes do trabalho | participation, Pessoa, contact, insert, audit | decisão + audit | `run():commitAuthorize()` após audit; commit |
| track | OUTREACH_WRITE + DISCIPLESHIP_CONFIGURE | `run()` e check provisional dedicado | insert/unique, audit FK | track + audit | `run():commitAuthorize()` revalida ambas após audit; commit |
| step | OUTREACH_WRITE + DISCIPLESHIP_CONFIGURE | `run()` e check provisional dedicado | track shared lock, insert/unique, audit FK | step + audit | `run():commitAuthorize()` revalida ambas após audit; commit |
| enroll | OUTREACH_WRITE | `run()`; DB clock antes do trabalho | participation, mentor, track, insert, audit FK | enrollment + audit de proveniência | `run():commitAuthorize()` após audit; commit |
| integrate | OUTREACH_WRITE | `run()`; DB clock antes do trabalho | participation, membership, insert, audit | evento + audit | `run():commitAuthorize()` após audit; commit |
| progress | OUTREACH_WRITE + scope de proveniência | transacção própria; clock provisional na autorização | enrollment exclusive, audit provenance shared, step/participation shared, duplicate lookup, insert, audit, provenance final | progress + audit ou id existente | scope final fail-closed, `commitAuthorize()` após último SQL; commit |
| history | OUTREACH_READ | transacção read-only | contact/followup reads | N/A | N/A; nenhum commit de write |

`progress()` compara a unidade recebida com a unidade da proveniência. A autorização é avaliada sobre a unidade real, para que um actor de outra unidade receba `ACTOR_NOT_AUTHORIZED`; proveniência ausente/ambígua recebe `ENROLLMENT_SCOPE_UNRESOLVED`; divergência de unidade passada por actor autorizado recebe `CONTEXT_MISMATCH`.

Os testes com locks mantêm a conexão holder em transacção; a libertação ocorre em `finally`. O supervisor elimina sinais e processos em `close()`, invocado em `finally`, inclusive em failure, exception ou timeout. Em PHP/Windows, pipes podem ignorar `stream_set_blocking(false)`; o supervisor consulta `proc_get_status()` e só drena stdout/stderr depois da saída do worker. Terminate, kill, verificação de liveness e `proc_close()` são controlados antes da limpeza final. O diretório temporário e os ficheiros têm namespace por `run_id`; um worker com crash nunca satisfaz `done` nem exit 0. O teste Wave 3 de sessões independentes voltou a usar o mesmo actor e token e claims criados pelo caminho normal. O holder bloqueia `event_sessions` da sessão alvo; o teste exige LOCK WAIT real desse worker e `done` do worker da outra sessão antes de libertar o holder.

## Limitação ambiental reproduzida (TEST-TIMING-01)

A reprodução repetida exigida pelo gate (50/50 isolado, 10 pares paralelos, 10 sob carga, sem retries) foi tentada várias vezes nesta máquina de desenvolvimento e não fechou de forma estável. A investigação isolou a causa ao ambiente local, não à lógica de domínio:

- **Docker Desktop sobre WSL2** (`Kernel Version: 6.18.33.2-microsoft-standard-WSL2`) neste posto de trabalho — classe de configuração conhecida por I/O de disco virtualizado imprevisível.
- **Latência de I/O/MySQL extrema e irregular** observada diretamente via `information_schema.processlist`/`innodb_trx` durante reproduções ao vivo.
- Uma `SELECT ... WHERE id = ? LIMIT 1` trivial (`event_sessions`, chave primária) foi observada presa **>27s** em estado `statistics` (fase de otimizador, antes sequer de tentar o lock).
- Uma única `CREATE TABLE` durante a migração de um schema de teste foi observada a demorar **>14s**.
- A taxa de sucesso das reproduções variou de forma ampla (~14% a ~80% consoante o lote) **sem correlação identificável com a lógica de domínio** — em todas as reproduções observadas ao vivo, a query correta foi sempre emitida na ordem correta pelo `CheckinService`/`DomainAccess`; variou apenas o tempo que o MySQL demorou a processá-la.
- O container Docker partilhado usado pelas reproduções anteriores tinha acumulado **85 schemas órfãos / 9665 tabelas** (o harness `scripts/wave4-m12/run.py` criava schema por corrida mas nunca o eliminava); um container novo e limpo foi usado para a revalidação, e o harness foi corrigido para eliminar o schema de cada corrida em `finally`.
- Dois containers Docker de um projeto não relacionado (`docker-web-1`, `docker-api-1` — projeto "kilsystem", não MEPA CRM) estavam em crash-loop (**475 reinícios**, ~149% CPU sustentado) a competir por recursos na mesma VM partilhada do Docker Desktop; foram parados pelo utilizador antes da revalidação.
- Tuning de MySQL testado (buffer pool maior, `innodb_flush_log_at_trx_commit=2`, `innodb_stats_persistent=OFF`) em runtime, sem persistir em código: **não resolveu a variabilidade** de forma consistente.
- Nenhum aumento adicional do timeout foi aplicado para forçar um PASS, e nenhuma lógica de retry foi introduzida para converter falhas em sucesso — ambos foram explicitamente excluídos como via de fecho deste item.

**Conclusão (na altura desta secção):** TEST-TIMING-01 permanece **ENVIRONMENT_BLOCKED / QUALIFICATION_PENDING**. A qualificação repetida (50/50, 10 pares, 10 sob carga, sem retries) deve ser reexecutada num ambiente com I/O de disco previsível (ex.: CI Linux nativo, ou este mesmo host após resolução da causa) antes de este item poder ser marcado RESOLVED.

*Nota de rastreabilidade:* a evidência bruta referida na secção "Evidência intermédia" abaixo (`wave4_m12_runs/regressions.json` e ficheiros `isolated_*`) foi gerada antes desta investigação e foi arquivada em `docs/database/physical/wave4_m12_runs/pre_fix_regressions/` e `pre_fix_25s_timeout/` respetivamente, para preservar o histórico sem confundir com as tentativas de revalidação descritas acima.

## Adenda — Migração XAMPP/Docker/WSL2 → WAMP: TEST-TIMING-01 RESOLVED — 2026-09-17

Esta adenda conserva integralmente as secções acima (histórico Docker/WSL2/Kaspersky); não as substitui. O runtime local mudou de XAMPP/Docker/WSL2 para MySQL nativo do WAMP; a qualificação de TEST-TIMING-01 foi refeita do zero neste novo ambiente, sem transportar pressupostos anteriores.

**Ambiente:** MySQL 8.4.7 (WAMP), `127.0.0.1:3306`, InnoDB, `root` sem senha, base viva `laravel`. PHP 8.1.33 (`C:\wamp64\bin\php\php8.1.33\php.exe`) e MySQL client (`C:\wamp64\bin\mysql\mysql8.4.7\bin\mysql.exe`) invocados por caminho absoluto — o `PATH` do sistema ainda referencia `C:\xampp\php`, um directório já removido pela migração; scripts que dependem de `php`/`node`→`php` bare (ex.: `check-database-capabilities.php` invocado via `validate-waveN-schema.cjs` a partir de `WaveOnePhysicalTest`/`WaveTwoPhysicalTest`) precisam de `PHP_BIN` explicitamente exportado no ambiente do processo pai.

**Defeitos de infra-estrutura encontrados e corrigidos no `my.ini` do WAMP** (nenhum é lógica de domínio; todos eram configuração de template do WampServer inadequada para uma app Laravel estrita):
1. `default_storage_engine=MYISAM` → `InnoDB`. MyISAM não suporta FKs nem `SELECT...FOR UPDATE`; migrations falhavam com "Specified key was too long" e teriam perdido toda a integridade referencial.
2. `sql_mode=""` (vazio) → `"ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION"` (o padrão de fábrica do MySQL 8, restaurado). Sem modo estrito ao nível do servidor, uma ligação que não passe por `strict=>true` do conector Laravel (ex.: `check-database-capabilities.php`, ferramentas externas, phpMyAdmin) aceita silenciosamente dados inválidos.
3. `max_connections=151` (default de fábrica) → `500`. Excedido (`Max_used_connections=152`) durante a bateria "parallel" da qualificação (2 pares concorrentes × suite completa); causava falhas genuínas de infra-estrutura (`SQLSTATE[08004] [1040] Too many connections`), não falhas de lock/timing.

Todas as três correcções foram aplicadas em runtime (`SET GLOBAL`, sem reiniciar o serviço) e persistidas no `my.ini` para sobreviver a um restart.

**Causa raiz real de TEST-TIMING-01 (não era Kaspersky):** reproduzida deterministicamente (100%, não intermitente) mesmo depois de excluir `C:\wamp64\bin\mysql\`, `C:\wamp64\bin\php\` e `C:\wamp64\www\mepa-crm\` do scan em tempo real do Kaspersky. Diagnóstico por cruzamento de fontes na mesma ligação, no mesmo instante:
- `SHOW ENGINE INNODB STATUS` mostra consistentemente `TRANSACTION ..., ACTIVE N sec inserting, LOCK WAIT ... RECORD LOCKS ... table organizational_units ... lock mode S locks rec but not gap waiting` — o lock é genuíno, cresce de forma monótona (9s→35s observado), e corresponde exactamente ao mecanismo de desenho (shared lock do FK-check bloqueado pelo `lockForUpdate()` do holder).
- `information_schema.innodb_trx`, consultado na mesma ligação e no mesmo instante, **nunca lista essa transacção** — apenas a do holder (`RUNNING`). Confirmado em 3 execuções completas + 5 capturas simultâneas consecutivas, sem excepção.
- Conclusão: `information_schema.innodb_trx` não reflecte este tipo de lock implícito (FK-check) nesta build de MySQL 8.4.7; `SHOW ENGINE INNODB STATUS` e `performance_schema.data_lock_waits` reflectem-no correctamente. O harness de teste (`waitForSqlWait()`/`waitForLockWait()`) dependia exclusivamente de `innodb_trx`, daí a falha 100% determinística — não uma falha de lógica de domínio, não flakiness de I/O.

**Correcção aplicada (código de teste, não de produção/domínio):** em `WaveFourCommitAuthorizationTest.php`, `WaveFourProgressCommitBoundaryTest.php` e `WaveThreeCheckinConcurrencyTest.php`, a consulta de deteção mudou de
`SELECT t.trx_query FROM information_schema.innodb_trx t JOIN information_schema.processlist p ON p.id=t.trx_mysql_thread_id WHERE p.db=? AND t.trx_state='LOCK WAIT'`
para
`SELECT p.info AS trx_query FROM performance_schema.data_lock_waits w JOIN performance_schema.threads t ON t.thread_id=w.requesting_thread_id JOIN information_schema.processlist p ON p.id=t.processlist_id WHERE p.db=?`
— mesma semântica de correspondência de texto no chamador (`str_contains(strtolower($row->trx_query), $expected)`), fonte de dados estrutural e oficialmente suportada (substituto moderno do antigo `INFORMATION_SCHEMA.INNODB_LOCK_WAITS`, removido no MySQL 8) em vez de uma view que se mostrou não fiável para este caso. Nenhuma lógica de domínio, migration ou `EvangelismService`/`DomainAccess` foi alterada.
