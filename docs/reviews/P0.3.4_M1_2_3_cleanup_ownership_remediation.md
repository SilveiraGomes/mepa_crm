## M122R-01 — Single failure boundary

### Root cause

Três chamadas a `_mysql()` dentro de `cleanup.py` não tinham nenhum
tratamento de excepção além de `except subprocess.TimeoutExpired`: a linha de
emissão do `DROP` dentro de `drop_database_verified()`, a linha de `KILL`
dentro de `kill_orphan_sessions()`, e todas as chamadas dentro de
`diagnostics_snapshot()` — invocada sempre que `out_dir` é passado, ou seja,
em toda corrida real de qualificação via `run_suite.py`, não apenas num caso
de canto de teste. Um `OSError` genuíno nestes pontos propagava sem ser
apanhado por `except VerificationError` em `cleanup_run()` (porque `OSError`
não é uma `VerificationError`), fazendo o harness inteiro crashar com uma
excepção não tratada em vez de reportar `CLEANUP_FAIL` estruturado. Para os
dois primeiros pontos (`DROP`, `KILL`), a schema ficava órfã sem qualquer
tentativa de rescue, porque o crash acontecia antes do bloco `except` que
dispara `rescue_cleanup()`.

### Call sites afectados (secção 3/4)

Inventariados por leitura exaustiva de `scripts/wave4-m121/` (todos os usos de
`_mysql()`, `subprocess.run()`, `subprocess.Popen()` e operações de
filesystem críticas):

| Call site | Antes | Depois |
|---|---|---|
| `drop_database_verified()` — emissão do `DROP` | só `except subprocess.TimeoutExpired: pass` | `mysql_exec(..., tolerate_timeout=True)` — timeout tolerado (comportamento intencional herdado de M1.2.1), `OSError`/exit≠0 → `CleanupInfrastructureError` |
| `kill_orphan_sessions()` — `KILL <id>` | sem tratamento algum | `OSError`/timeout → `CleanupInfrastructureError`; um `KILL` que corre mas falha porque a thread já desapareceu (corrida benigna, esperada) continua tolerado, não é fatal |
| `diagnostics_snapshot()` — 4 queries de diagnóstico | sem tratamento algum | cada query independentemente guardada; uma falha aqui nunca propaga (best-effort por natureza, secção 5 da doc M1.2.2), apenas anota o erro no snapshot |
| `schema_exists()` / `referencing_sessions()` | já correctas (M1.2.2) | inalteradas na semântica externa; agora implementadas sobre `mysql_exec()` |
| `orphan_schemas()` (`verify.py`) | já correcta (M1.2.2) | reescrita sobre `cleanup.mysql_exec()`, mesmo contrato externo |
| `orphan_php_processes()` (`verify.py`) | já correcta (M1.2.2), único call site não-MySQL (`tasklist`) | inalterada |
| `barriers_present()` — `Path.exists()` | já correcta (M1.2.2) | inalterada |

### Fix

Boundary único centralizado, `mysql_exec(statement, timeout, tolerate_timeout=False)`
em `cleanup.py`: a ÚNICA função do módulo que invoca `subprocess.run()` para
um comando MySQL fora do wrapper de baixo nível `_mysql()` (mantido
inalterado por compatibilidade — vários scripts de auditoria fora do âmbito,
`scripts/audit-wave4-m121r/` e `scripts/audit-wave4-m122r/`, chamam-no
directamente e esperam um `CompletedProcess`). `mysql_exec()` normaliza
`subprocess.TimeoutExpired`, `OSError` e exit≠0 num novo tipo de excepção
explícito, `CleanupInfrastructureError` — distinto de `VerificationError`
("recurso não pode ser confirmado"), mas com o mesmo destino final: ambos são
apanhados de forma idêntica no boundary de topo de `cleanup_run()`.

`cleanup_run()` ganhou o contrato exacto pedido na secção 5:

```
try:
    all_absent = _run_primary_cleanup(...)
except CleanupInfrastructureError as exc:
    verification_error = str(exc)
except VerificationError as exc:
    verification_error = str(exc)
except Exception:
    # erro de programação inesperado: rescue defensivo, depois re-raise
    try: rescue_cleanup(...)
    except Exception: pass
    raise
```

`verification_error is not None` funde ambos os tipos conhecidos no mesmo
caminho `CLEANUP_FAIL` + rescue já existente desde M1.2.2 — nenhum caminho
novo de decisão foi introduzido (secção 17). Um erro genuinamente inesperado
(nem `CleanupInfrastructureError` nem `VerificationError`) já não pode deixar
um recurso abandonado silenciosamente: o `except Exception:` tenta sempre um
rescue best-effort primeiro, e só depois relança a excepção original — para
que continue a aparecer como o bug que é, nunca como um `CLEANUP_FAIL` de
rotina.

`rescue_cleanup()` foi endurecido com a mesma defesa em profundidade: os seus
próprios `except VerificationError` foram alargados para
`except (VerificationError, CleanupInfrastructureError)` em cada ponto onde
chama uma função de verificação — o rescue é a última linha de defesa contra
um recurso abandonado, e não pode deixar escapar nenhuma classe de erro de
observabilidade, mesmo uma que não esperasse estritamente.

`schema_exists()`/`referencing_sessions()` continuam a devolver
`bool`/`list[dict]` e a lançar `VerificationError` numa falha — agora
implementadas sobre `mysql_exec()`, capturando `CleanupInfrastructureError` e
relançando como `VerificationError`, preservando 100% o contrato externo já
usado por `scripts/audit-wave4-m121r/`/`scripts/audit-wave4-m122r/` em
contexto booleano.

## M122R-02 — Ownership por identidade

### Modelo antigo (timing)

`run_suite.py::run_one()` tirava um snapshot de `verify.barrier_dirs()` antes
e depois do processo PHPUnit; qualquer directório novo nesse intervalo era um
"candidato" que `cleanup_run()` verificava e, em caso de sobrevivência,
`rescue_cleanup()` apagava incondicionalmente com `shutil.rmtree()`. A
auditoria M1.2.2-R confirmou empiricamente (6/40 corridas `parallel` reais,
em duas baterias completas independentes) que um directório podia aparecer
como candidato de uma corrida sem ter sido criado por ela — resolvido sempre
sem rescue nas amostras observadas, mas sem nenhuma verificação de posse
antes da remoção forçada.

### Modelo novo (identidade)

Cada corrida ganha a sua própria raiz, criada e conhecida **antes** do
processo de domínio arrancar (secção 7 — "a run conhece o caminho antes de
iniciar"):

```
<tempdir>/wave4-m121/<run_id>/
  .owner.json   { run_id, database_name, created_at, harness_version }
```

`run_suite.py::run_one()` chama `cleanup.create_run_root(run_id, schema)`
imediatamente a seguir ao `CREATE DATABASE`, antes de `subprocess.Popen()`. O
`run_id` é agora extraído de forma centralizada por `run_id_of(schema)` (nova
função — substitui o `schema.rsplit("_", 1)[-1]` ad hoc duplicado por vários
chamadores).

`verify_ownership(root, run_id, schema)` é a única autoridade sobre se `root`
pode ser tratado como propriedade desta corrida — verdadeiro apenas se
**todos**:
- `root`, canonicalizado (`Path.resolve()`), corresponde **exactamente** ao
  caminho esperado derivado de `run_id` (nunca um prefixo/ancestralidade —
  isto rejeita sozinho a própria `RUN_ROOT_BASE`, a raiz do temp do sistema, a
  raiz do repositório, uma raiz de drive, qualquer sequência de traversal, e
  qualquer symlink que resolva para outro lado);
- existe um `.owner.json` dentro dele;
- o seu `run_id` e `database_name` correspondem exactamente aos do chamador.

`safe_remove_run_root()` é a **única** função em todo o módulo autorizada a
`shutil.rmtree()` — recusa (com um `RuntimeError` duro, não um `False`
silencioso) a menos que `verify_ownership()` passe.

`FILES_REMOVED` deixou de depender do diff temporal de barriers (secção 15):
o caminho primário de `cleanup_run()` agora **remove activamente** (não só
verifica) a raiz própria via `safe_remove_run_root()`, e só marca
`files_removed_at` depois dessa remoção ter sido confirmada. O diff legado
(`candidate_barriers`) é mantido como **diagnóstico puro** (secção 14) — o seu
resultado, e mesmo um erro ao recolhê-lo, nunca mais influenciam
`FILES_REMOVED`, `CLEANUP_VERIFIED` ou `PASS` (ver `t4b`/`t5b`, abaixo, que
provam deliberadamente o inverso do comportamento de M1.2.2).

### Database ownership (secção 10)

`validate_database_ownership(schema, run_id)` — hard guard chamado por
`cleanup_run()` sempre que um `run_root` é fornecido (backward-compatible:
chamadas legadas sem `run_root`, como os cenários A–H de `test_cleanup.py`,
continuam a usar apenas rótulos informais como `run_id`, sem esta validação
estrita) e por `create_run_root()` incondicionalmente. Confirma que o
`run_id` embebido na schema corresponde exactamente ao `run_id` que o
chamador afirma ser — impossível para uma corrida operar sobre a schema de
outra por engano.

### Rescue recebe exactamente a mesma guarda (secção 11)

`rescue_cleanup()` já não chama `shutil.rmtree()` sobre nenhum
`candidate_barriers` — essa capacidade foi **removida por completo**,
fechando o risco de eliminação entre corridas na raiz. O único recurso de
filesystem que o rescue pode remover é `run_root`, exclusivamente através de
`safe_remove_run_root()` — a mesma função, a mesma verificação de posse, sem
nenhum caminho de permissão mais ampla.

### Prova (ownership tests, O1–O9)

| Teste | Prova |
|---|---|
| O1 | `safe_remove_run_root(root_b, run_id_a, schema_a)` → `RuntimeError`; raiz de B intacta |
| O2 | `validate_database_ownership(schema_b, run_id_a)` → `RuntimeError`; DB de B intacta |
| O3 | marker com `run_id`/`database_name` errados → `verify_ownership()` devolve `False`, remoção recusada |
| O4 | marker ausente → `verify_ownership()` devolve `False`, remoção recusada |
| O5 | 7 variantes de traversal/`run_id` inválido (`../../../etc`, `..`, separadores mistos, string vazia, não-hex, hex de comprimento errado) → todas recusadas na construção do caminho, antes de qualquer verificação de posse |
| O6 | tentativa directa sobre `RUN_ROOT_BASE` (a própria base) → recusada; base ainda presente |
| O7 | symlink a apontar para um directório "isco" fora da raiz própria → `verify_ownership()` recusa, isco intocado (ou N/A registado explicitamente se o SO/permissões não suportarem a criação do symlink) |
| O8 | **teste obrigatório da secção 12**: par paralelo real, corrida A forçada a `CLEANUP_FAIL`+rescue enquanto B corre concorrentemente e passa normalmente — A nunca remove a raiz de B, B remove a sua própria com sucesso |
| O9 | corrida limpa: `PASS`, `FILES_REMOVED` confirmado, raiz e schema genuinamente ausentes, 0 rescue |

Nota de desenvolvimento honesta: a primeira versão de O8 usava
`cleanup.MYSQL`/`cleanup.CLEANUP_TIMEOUT_SECONDS` (globais ao nível do
módulo) para forçar a falha de A — isto **corrompeu B** também, porque os
dois threads partilham o mesmo processo Python e portanto o mesmo espaço de
globals; não há isolamento por thread destas variáveis. Corrigido substituindo
por um mock discriminador de `safe_remove_run_root` que decide pelo `run_id`
recebido (força falha só para A, delega para a implementação real para
qualquer outro `run_id`, incluindo os de B) — thread-safe por construção,
independentemente da interleaving real dos dois threads. Este mesmo padrão é
o usado na bateria de 20 pares (abaixo).
