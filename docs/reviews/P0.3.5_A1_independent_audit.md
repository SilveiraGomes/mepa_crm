# Findings

## A1R-01

**Severity:** HIGH
**Category:** EVIDENCE
**Product blocker:** NO
**Evidence blocker:** YES
**Wave blocker:** YES

**Requirement:** Mission Section 37 requires confirming, via a simple direct proof, that the Test Infrastructure V2 dedicated MySQL 8.4.7 instance genuinely starts/stops as claimed, so that all live-DB evidence gathered through it can be trusted. ADR-0014 requires that any infrastructure finding be *proven* (not assumed) unable to produce a false PASS, hide a real failure, damage another run's resources, or invalidate critical evidence before it can be classified as non-blocking `TEST_INFRA_DEBT`.

**Evidence:** Running `python tools/test-infrastructure/mysql_instance.py init-start --port 3307 --datadir <fresh dir>` — the exact documented invocation, on the exact documented port — returned `{"status": "STARTED", ...}`. Independently querying that instance (`SELECT VERSION(), @@datadir, @@port`) returned `11.4.9-MariaDB` / `c:\wamp64\bin\mariadb\mariadb11.4.9\data\` / `3307` — **not** MySQL 8.4.7. The tool's own log for that exact attempt (`mysqld.err`) shows the real MySQL 8.4.7 process it spawned logged `Can't start server: Bind on TCP/IP port` / `Do you already have another mysqld server running on port: 3307 ?` and cleanly aborted — yet `start()` still reported `STARTED`, because it verifies readiness solely via `mysqladmin ping` succeeding against the target host:port, never checking that the process answering is the one it just spawned (the same class of bug already found and fixed in this tool's `stop()` by `P0.3.5-A1.0` — this is the un-fixed mirror case in `start()`).

Root cause: a genuine, independently-running WAMP Windows service (`wampmariadb64`, MariaDB 11.4.9) is permanently bound to port 3307 on this machine (`Get-CimInstance Win32_Service`: `State=Running`). Its own error log shows a single, uninterrupted start event on **2026-09-17 13:55:03** with no shutdown since — i.e., it was already occupying port 3307 continuously through the entire Wave 5 implementation window (all three audited commits are dated 2026-09-18).

**Independent reproduction / corroboration beyond this audit's own attempt:** `mepa_wave3_test_pool_01`, `mepa_wave4_test_pool_01`, `mepa_wave4_test_pool_02` — the exact synthetic pool database names `tools/test-infrastructure/pool.py` creates — **already existed** on this MariaDB service before this audit ran anything on port 3307. These can only have been created by an earlier `pool.py create-and-migrate --port 3307` run whose migration subprocess connected to whatever was actually listening on 3307 at the time. Given the service's proven continuous uptime since before the Wave5 window, this is strong evidence that at least the Wave 3/Wave 4 Test Infrastructure V2 pool evidence (referenced in project history as underpinning the current Wave 4 "APPROVED WITH DEBT" gate) was gathered against this same shared, non-disposable, wrong-engine service rather than a genuinely isolated instance.

**Discriminating test:** MariaDB's CHECK-violation error code was directly probed and confirmed to be `4025`, not MySQL's `3819`. `WaveFivePhysicalTest.php` hardcodes `assertSame(3819, ...)` for all 6 CHECK-violation cases. Had the documented "OK (7 tests, 2272 assertions)" PHPUnit run actually executed against this MariaDB service, that assertion would have failed loudly — which this audit cannot reconcile with the claimed clean result. This audit cannot prove with certainty whether the original A1 PHPUnit run specifically hit this collision or happened to avoid it; what it *has* proven is that **the tooling provides no way to tell the difference**, and that the identical claim ("verified against a dedicated MySQL 8.4.7 instance, port 3307") demonstrably was *not* true for at least the persisted Wave 3/4 pool evidence.

**Independent reproduction:** ADR-0014's five TEST_INFRA_DEBT exemption criteria were checked against this evidence, not assumed: criteria (b) "cannot produce a false PASS", (c) "cannot hide a real failure", and (d) "cannot damage another run's resources" are all directly **refuted** by the reproduction above (not merely theoretical risk). This fails the exemption test and cannot be classified as non-blocking debt.

**Expected:** `init-start` either genuinely binds the claimed MySQL 8.4.7 process on the requested port, or fails closed with a clear error — never silently substitutes an unrelated, wrong-engine, non-disposable service while reporting success.
**Actual:** False `STARTED`; the tool cannot currently distinguish "my dedicated instance is ready" from "something else already answers pings on this port."
**Impact:** Undermines the trustworthiness of every "verified against a dedicated MySQL 8.4.7 instance, port 3307" claim in `P0.3.5_A0_academy_design.md`, `P0.3.5_A1_wave5_physical_implementation.md`, and `P0.3.5_A1_0_pre_audit_evidence_hygiene.md` (and, by the Wave 3/4 pool-database evidence above, in the Wave 4 gate's own Test Infrastructure V2 pilot). Does **not** imply the physical schema itself is wrong — this audit independently re-derived and re-verified every physical/product claim on a genuinely verified instance and found the schema correct throughout.
**Affected tables/files:** `tools/test-infrastructure/mysql_instance.py` (`start()`/`init-start`), and by extension every consumer that trusts its `STARTED` status: `tools/test-infrastructure/pool.py`, `apps/api/tests/DatabaseV2/Support/migrate_pool_db.php`, `apps/api/tests/Database/Support/WaveFiveCase.php`/`WaveFourCase.php` and their test suites.
**Recommended remediation:** After `mysqladmin ping` succeeds, `start()` must additionally verify the responding server is the specific process it just spawned (same PID/datadir-ownership technique `stop()` now uses, per `P0.3.5-A1.0`) **and** reports the expected MySQL version — failing closed (e.g. `BIND_FAILED`) rather than `STARTED` otherwise. Not applied during this audit (out of scope — no correction during audit, per mission Section 46).
