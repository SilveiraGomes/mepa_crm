## 3. Generated column — inspecção directa

`SHOW CREATE TABLE transfers` e `information_schema.COLUMNS` (não apenas os testes PHP):

```
closed_at   datetime(6) DEFAULT NULL
open_flag   tinyint unsigned GENERATED ALWAYS AS (if((`closed_at` is null),1,NULL)) STORED
UNIQUE KEY  uq_transfers_membership_open (membership_id, open_flag)
```

`GENERATION_EXPRESSION` confirmado literalmente: `if((`closed_at` is null),1,NULL)`. `EXTRA`
confirmado: `STORED GENERATED` (não `VIRTUAL`). `IS_NULLABLE` de `open_flag` = `YES` (obrigatório
para a semântica `NULL` distinto do MySQL funcionar).

**Sequência exacta pedida, testada em SQL puro (nenhum PHP envolvido)** contra a mesma
membership: duas linhas `COMPLETED` (closed_at preenchido) + uma `CANCELLED` (closed_at
preenchido, effective_at nulo) — as três coexistem sem erro. Uma linha `OPEN` (closed_at nulo)
— aceite. Uma **segunda** linha `OPEN` para a mesma membership — **rejeitada**:

```
ERROR 1062 (23000): Duplicate entry '1-1' for key 'transfers.uq_transfers_membership_open'
```

Fechada a linha aberta (`UPDATE ... SET closed_at=...`), uma nova linha `OPEN` volta a ser aceite.
Confirma exactamente o comportamento pedido na secção 3 do pedido.

## 12. Idempotência — mecanismo determinado com precisão

Confirmado estruturalmente (`information_schema.COLUMNS`): **não existe nenhuma coluna
`idempotency_key`/`client_key` em `transfers`.** A segurança de reenvio (`retry-safety`) depende
inteiramente de **(lock da membership + `UNIQUE` física)**, não de uma chave de idempotência
dedicada. Diferença importante e correctamente já documentada pelo próprio relatório M1: ao
contrário do `MemberNumberGenerator` (que devolve o número existente em replay), um `request()`
repetido **não devolve o ID da transferência original** — apenas rejeita de forma limpa. Quem
precisar do ID existente tem de o procurar separadamente (`open_flag=1` para essa membership).
**Não foi inferida nenhuma garantia que o código não possui** — a alegação do relatório M1 já era
precisa nesta distinção, e a auditoria independente confirma-a.

## 14. Rollback / remigrate da migration M1 — **PROBLEMA ENCONTRADO**

Reproduzido de forma limpa e inequívoca via `Migrator` explícito (não `artisan` CLI com
adivinhação de batch, que se mostrou ela própria frágil e confusa numa base com dados inseridos
manualmente fora do Migrator — ver nota metodológica no fim desta secção).

Sequência: aplicar M1 → confirmar guard presente → **inserir histórico realista** (1
`COMPLETED`, 1 `CANCELLED`, 1 `PENDING`/aberta, para a mesma membership, via query builder) →
rollback apenas de M1 → confirmar guard removido e Wave 2 intacta → **reaplicar M1**.

Resultado:

- Rollback: **sucesso** — `closed_at`/`open_flag` removidas, índice único removido, Wave 2
  continua com as 78 tabelas. As 3 linhas de `transfers` sobrevivem como **linhas** (nenhuma é
  apagada), mas **o conteúdo de `closed_at` é permanentemente perdido** (consequência inevitável
  de um `DROP COLUMN`, mas com efeito prático grave aqui — ver abaixo).
- Reaplicar M1: **FALHA**:
  ```
  SQLSTATE[23000]: Integrity constraint violation: 1062 Duplicate entry '1-1' for key
  'transfers.uq_transfers_membership_open' (SQL: ALTER TABLE `transfers` ADD UNIQUE KEY
  `uq_transfers_membership_open` (`membership_id`, `open_flag`))
  ```

**Causa raiz:** ao remover `closed_at`, perde-se a distinção entre as transferências que estavam
fechadas e a que estava aberta. Ao readicionar `closed_at` (nova, `NULL` por omissão), **as três
linhas ficam todas com `closed_at IS NULL`**, logo `open_flag=1` para todas — três linhas
"abertas" para a mesma membership. A criação do `UNIQUE KEY` falha porque os próprios dados,
reconstruídos incorrectamente, já violam o invariante que esse índice deveria impor.

**Isto significa, em produção real (não apenas em teste):**
1. Um rollback desta migration numa base com transferências históricas reais **apaga
   silenciosamente, de forma irreversível, a distinção entre transferências abertas e
   fechadas** — no instante em que o `down()` corre, antes de qualquer tentativa de reaplicar.
2. Uma tentativa subsequente de reaplicar a migration **falha completamente**, deixando o
   deployment sem o guard físico activo e com a migration presa em estado `Pending`, exigindo
   intervenção manual para resolver.

Isto corresponde directamente a **dois** dos critérios HIGH explicitamente listados no pedido:
*"rollback deixar estado corrupto"* e, de forma mais restrita, *"solução destruir histórico"*
(destrói especificamente a informação de quando/se cada transferência foi encerrada — as linhas
em si sobrevivem, mas essa informação não).

**Nota metodológica:** a primeira tentativa de reproduzir este cenário usando `artisan
migrate:rollback --step=1` directamente sobre uma base que também tinha sido alimentada com dados
via SQL em bruto produziu resultados confusos e inconsistentes entre si (o `--step=1` acabou por
reverter, numa segunda tentativa, uma migration diferente da Wave 2 depois de M1 ter ficado
`Pending` devido à falha acima) — isto é uma fragilidade da forma ad-hoc de testar via CLI
sobre uma base "suja", não uma alegação adicional sobre o comportamento da migration em si; a
reprodução **definitiva e fidedigna** é a feita via `Migrator` explícito documentada acima, e é
essa que sustenta o achado.

**Confirmado que isto não afecta a operação normal para a frente** (sem nunca fazer rollback):
todos os cenários de concorrência, histórico e criação normal (secções 5, 6, 9, 10) continuam
correctos. O problema é especificamente do caminho `down()`/reaplicação sobre dados já
existentes.

Critérios para `RESOLVED` (secção 20 do pedido): concorrência reproduzida independentemente ✅;
DB guard funciona sozinho ✅; application guard funciona ✅; histórico continua permitido ✅;
memberships independentes não se bloqueiam globalmente ✅; **rollback/remigrate passar ❌**

Como o critério de rollback/remigrate **falha** sob condições realistas (tabela com histórico),
`RESOLVED` não pode ser usado. A garantia central de concorrência (o problema original de
F-W2F-01) está solidamente provada e não tem nenhum achado CRITICAL/HIGH contra si própria — o
problema é especificamente na reversibilidade da migration, uma lacuna nova, contida e bem
compreendida, não uma falha da solução de concorrência em si.

**Decisão: CONDITIONALLY APPROVED → mapeado para "CORRECÇÃO NÃO APROVADA"** até F-M1R-01 ser
corrigido (por exemplo, `down()` não remover fisicamente as colunas, ou preservar o histórico de
`closed_at` antes de as remover, ou documentar e bloquear operacionalmente qualquer rollback desta
migration em ambientes com dados reais). Recomenda-se uma tarefa dedicada P0.3.2-M1-F2, seguindo
o mesmo padrão já estabelecido (achado → correcção → re-auditoria).
