## 2. Test Infrastructure V2 — bug de `stop()`

### Reprodução

Executado exactamente como pedido: **processo A** (`init-start`) numa invocação, **processo B** (`stop`, nova invocação CLI separada) noutra. Evidência: `docs/database/physical/wave5_a1_0_evidence/mysql_instance_stop_bug_reproduction.json`.

```
Processo A: init-start -> {"status": "STARTED", "port": 3307, ...}
Verificação pré-stop: mysqladmin ping -> "mysqld is alive"
Processo B (separado): stop -> {"mysqld_stopped": true, ...}   <- SUCESSO FALSO
Verificação pós-stop, independente do resultado do tool:
  netstat -> 127.0.0.1:3307 LISTENING (ainda activo)
  mysqladmin ping -> "mysqld is alive" (ainda vivo)
```

Confirmado: `stop` retornou sucesso; **mysqld continuou vivo; a porta continuou aberta; nenhum `mysqladmin shutdown` foi realmente enviado** pela invocação separada.

### Causa raiz (Secção 4)

`MysqlInstance.stop()` decidia toda a acção de shutdown com base em `self.process is not None and self.process.poll() is None` — um handle `subprocess.Popen` que só existe **em memória, dentro do mesmo objecto Python** que chamou `start()`. Uma invocação CLI separada de `stop` cria um `MysqlInstance` novo com `self.process = None`, pelo que a condição era sempre falsa e o código caía directamente em `else: result["mysqld_stopped"] = True` — sem nunca verificar porta, PID, ou enviar qualquer comando de shutdown.

Mecanismos de identidade disponíveis, e o que estava a ser usado:
- **PID file**: `mysqld` já escreve o seu próprio `--pid-file` no datadir (`mysqld.pid`) — existia, mas nunca era lido pelo `stop()` anterior.
- **datadir/port**: já passados explicitamente como argumentos `--datadir`/`--port` ao CLI `stop`, mas nunca usados para verificar identidade.
- **mysqladmin**: já disponível e usado no `stop()` anterior, mas apenas dentro do ramo `if self.process...` que uma invocação separada nunca alcançava.
- **Nenhum ficheiro de metadata de sessão própria existia antes desta tarefa.**

### Instância com identidade persistente (Secção 5)

`start()` passou a escrever `<datadir>/../session.json` com `port`, `datadir`, `pid`, `started_at`, `mysqld_path` — não como única fonte de verdade, mas como registo adicional de diagnóstico. A fonte de verdade primária para resolução de PID entre invocações é o próprio `mysqld.pid` do MySQL (autoritativo, sempre presente enquanto o processo corre), consultado apenas quando não existe handle em memória (T1 continua a preferir o handle real).

### `stop()` correcto (Secção 6) — implementado exactamente nesta ordem

1. **Localizar**: se a porta não responde a `mysqladmin ping`, retorna `ALREADY_STOPPED` (idempotente, T3) sem qualquer acção.
2. **Confirmar pertença**: resolve o PID (handle em memória > `mysqld.pid`), consulta `Get-CimInstance Win32_Process` (PowerShell, sem dependências novas) para obter `Name`+`CommandLine` reais, e só declara `ownership_verified=true` se o `CommandLine` contiver exactamente `--datadir=<este datadir>` **e** `--port=<esta porta>` — nunca confia no número de PID ou de porta isoladamente.
3. **Confirmar activa**: já feito no passo 1.
4. **Shutdown limpo**: `mysqladmin shutdown` é **sempre** tentado, independentemente de a pertença ter sido verificada — este comando fala apenas com o servidor MySQL que responde exactamente nesse host:porta, nunca com um processo do SO arbitrário, pelo que é seguro mesmo sem verificação de pertença.
5. **Aguardar**: sondagem (até 30s) até `mysqladmin ping` deixar de responder.
6. **Confirmar inactivo**: só depois de a porta deixar de responder — e, quando havia PID verificado, de a entrada de processo desaparecer — é que se declara sucesso.
7. **Só então retorna SUCCESS.**

### Fail closed (Secção 7)

Se a porta ainda responde depois do timeout, `stop()` retorna **`STOP_FAILED`**, nunca `SUCCESS`. Nenhum `taskkill` é disparado com base apenas no número de porta.

### Fallback (Secção 8)

Um fallback `taskkill /PID <pid> /F` limitado no tempo só é tentado quando: (a) a pertença já tinha sido verificada, **e** (b) essa pertença é **reconfirmada imediatamente antes do kill** (estreita, nunca elimina, a janela TOCTOU). Se a reconfirmação falhar, o fallback é recusado e fica registado em `notes`. `127.0.0.1:3306`/`laravel` está protegido de forma absoluta: `MysqlInstance.__init__` levanta `ValueError` (não `assert`, que `-O` remove) sempre que `port == 3306` — nenhum caminho de código deste módulo consegue sequer construir um objecto apontado à base de dados da aplicação.

## 5. Classificação ADR-0014 (Secção 11)

**TEST_INFRASTRUCTURE.** O bug nunca alterou comportamento de produto e nunca afectou nenhuma evidência já recolhida em P0.3.5-A1 (toda a evidência de A1 foi obtida enquanto a instância estava genuinamente activa, antes de qualquer `stop()`), pelo que **não invalida retroactivamente** o veredicto "PHYSICAL SCHEMA READY FOR INDEPENDENT AUDIT". É fechado aqui porque `STOP_SUCCESS` falso é um risco de fiabilidade de **EVIDENCE** para corridas futuras (um chamador que confiasse em `mysqld_stopped: true` poderia deixar instâncias órfãs ou assumir falsamente um ambiente limpo para a sessão de testes seguinte). Com a correcção: `STOP_SUCCESS` agora implica genuinamente `INSTANCE_STOPPED_CONFIRMED` (provado na Secção 4 acima).

## 11. Saída final estruturada

**Test infrastructure bug:**
Reproduction: confirmada — `stop` numa invocação CLI separada retornava `mysqld_stopped: true` com mysqld genuinamente ainda vivo (porta LISTENING, `mysqladmin ping` respondia).

3306 guard: `ValueError` incondicional em `__init__` se `port == 3306`; confirmado por teste (T9) e nunca invocado contra a app DB ao longo de toda a tarefa (127 tabelas, inalterado).
