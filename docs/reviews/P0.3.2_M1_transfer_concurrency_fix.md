# P0.3.2-M1 — Correcção F-W2F-01 (Concorrência de Transferências)

**Finding:** F-W2F-01 — `transfers` não tinha nenhuma restrição física que impedisse duas
transferências `PENDING` concorrentes e incompatíveis (destinos diferentes) para a mesma
`membership_id`. Identificado em `docs/reviews/P0.3.2_wave2_independent_reconciliation.md`
(secção "Achados", `test_two_concurrent_transfers_for_the_same_membership_are_not_physically_guarded`
em `WaveTwoIndependentReconciliationTest.php`).

## Causa raiz

`transfers` tinha `membership_id` como coluna indexada mas não única — nada na base de dados nem
na camada de serviço (não existia serviço dedicado; as escritas eram inserções directas)
impedia duas linhas `PENDING` para a mesma membership. Não havia janela de "check depois insere"
explícita na aplicação porque não havia aplicação nenhuma a escrever `transfers` — o problema era
a ausência de qualquer enforcement, não um bug num enforcement existente.

## Leitura prévia (evidência documental consultada)

- `docs/database/01_database_principles.md`, linha 35: *"lock_version dá compare-and-swap de
  rascunho, não garante agregados. Autorizar backend, bloquear âncoras preexistentes em ordem,
  validar, gravar fontes+auditoria+outbox num commit."* — confirma institucionalmente que a
  opção D (optimistic concurrency via `lock_version`) **não** é adequada para este tipo de
  invariante entre linhas (agregado), e que o padrão aprovado é bloquear a âncora (aqui,
  `memberships`) antes de validar e escrever.
- `docs/database/04_database_constraints.md`, linha 53: *"Ordem de locks documentada por
  operação: gerador idempotência→membership→contador... Todos os writers seguem mesma ordem."*
  — o `MemberNumberGenerator` já segue este padrão; a correcção estende-o naturalmente a
  `TransferService`, sem inventar uma ordem nova.
- `docs/database/04_database_constraints.md`, linha 43: *"Lists/event/registration, académico e
  workflow/import precisam de catálogo exacto por tabela e transições D-11 antes de migrations...
  Não aceitar status livre nem reutilizar catálogo universal."* — `transfers.status` **não**
  tem vocabulário institucional fixado (D-11 ainda pendente para esta tabela especificamente:
  não consta na lista de "Estados propostos" dessa mesma secção). Por isso a invariante desta
  correcção foi desenhada para **não depender de nenhuma string de `status`** — evita alterar ou
  antecipar uma regra institucional ainda não decidida.
- `mepa_crm_v1.1.1.md`, linha ~1066: fluxo canónico da Transferência — *"Pedido → Validação de
  Origem → Aceitação do Destino → Efectivação"*. O estágio terminal "Efectivação" já corresponde
  à coluna `effective_at`, já aprovada no catálogo (nula até à efectivação). A correcção introduz
  apenas a coluna irmã `closed_at`, que fecha o ciclo tanto para efectivação como para
  cancelamento/rejeição sem nunca ter chegado a `effective_at`.

## Solução

**Opções avaliadas (secção 3 do pedido):**

| Opção | Avaliação |
|---|---|
| A. `SELECT ... FOR UPDATE` sobre `memberships` | Necessária mas não suficiente sozinha — bloqueia escritores da mesma membership entre si, mas não impede, por construção, que uma segunda transacção insira antes de a primeira validar sob isolamento `REPEATABLE READ` sem uma segunda camada física. Usada como âncora (ver D-01/04_database_constraints), não como única defesa. |
| B. Lock sobre linha/estado de transferência existente | Não resolve o problema central: não se pode bloquear uma linha que ainda não existe. Descartada como mecanismo primário. |
| **C. Constraint derivada + UNIQUE** | **Escolhida.** Coluna gerada `open_flag` (1 enquanto `closed_at IS NULL`, `NULL` quando fechada) + `UNIQUE(membership_id, open_flag)`. MySQL trata `NULL` como distinto em índices `UNIQUE`, pelo que múltiplas linhas fechadas coexistem livremente e apenas uma aberta é permitida por membership — o equivalente nativo em MySQL a um índice único parcial do Postgres, **não** uma imitação de sintaxe Postgres (nenhum `WHERE` de índice, apenas uma coluna gerada `STORED` genuína). |
| D. Optimistic concurrency / `lock_version` | Descartada para este invariante — ver citação de `01_database_principles.md` acima: `lock_version` serve compare-and-swap de uma linha, não garante um agregado (contagem de linhas abertas por membership). |
| **E. Transacção + lock + validação** | **Combinada com C.** `TransferService::request()` corre inteiramente dentro de uma transacção, bloqueia `memberships` primeiro (mesma ordem já usada por `MemberNumberGenerator`), e confia na `UNIQUE` física como o backstop definitivo contra TOCTOU — mesmo que duas transacções concorrentes passem ambas por uma leitura optimista sob `REPEATABLE READ`, a segunda `INSERT` falha sempre no motor de armazenamento, independentemente do que a sua própria snapshot mostrava. |

Não foi criado trigger. Não foi criado índice único parcial "fictício" de Postgres — a coluna
gerada `STORED` é uma funcionalidade nativa e documentada do MySQL 8.

## Camada de enforcement

Física (UNIQUE sobre coluna gerada) **e** aplicação (`TransferService`, que bloqueia a âncora e
traduz a violação física numa excepção de domínio). As duas camadas são redundantes por desenho:
a física é a garantia definitiva sob concorrência real; a aplicação existe para dar uma mensagem
de erro limpa e auditável em vez de deixar escapar uma `QueryException` genérica.

## Lock utilizado

`SELECT ... FOR UPDATE` sobre a linha de `memberships` (mesma âncora e mesma ordem que
`MemberNumberGenerator`: nenhum novo tipo de lock, nenhuma nova ordem de locks documentada é
necessária). Granularidade: por `membership_id`. Duas memberships diferentes nunca partilham
lock nenhum — confirmado em teste (secção Testes, cenário 10).

## Transacção

`TransferService::request()`, `effectuate()` e `cancel()` correm cada uma dentro de
`$this->db->transaction(...)`, seguindo exactamente o mesmo padrão de
`MemberNumberGenerator::generateFor()`.

## Idempotência

- `request()` **não** é idempotente por reenvio silencioso (cada pedido é uma tentativa nova),
  mas é **seguro para repetir** (retry-safe): uma segunda tentativa idêntica falha de forma limpa
  com `TRANSFER_ALREADY_IN_PROGRESS`, nunca duplica a linha aberta.
- `effectuate()` e `cancel()` são idempotentes: reaplicar a mesma operação sobre uma transferência
  já fechada no mesmo sentido é um no-op silencioso; aplicá-las em sentido incompatível
  (`effectuate` sobre uma já cancelada, ou vice-versa) lança uma excepção de domínio específica.

## Impacto de performance

Lock estritamente por `membership_id` (nunca global). Duas memberships diferentes nunca esperam
uma pela outra — confirmado empiricamente no cenário 10 (10 memberships concorrentes, sem
bloqueio cruzado, tempo de parede sob 10s). Sob contenção extrema na MESMA membership (cenário 8,
20 workers), o custo é apenas o tempo de fila normal de um `SELECT FOR UPDATE` mais uma tentativa
de `INSERT`/`UNIQUE` — sem deadlock nem timeout observado em nenhuma das execuções reais.

confirmado por consulta directa a `information_schema` antes/depois). **Nenhuma migration já
aplicada da Wave 2 foi editada.** Caminho de upgrade preservado: a migration aplica-se sobre
qualquer base já em Wave 2, sem exigir recriação.

Deliberadamente **não** foi actualizado `scripts/lib/wave2-catalog.cjs`/`model_catalog.json` para
incluir estas colunas — essa é a fronteira exacta do âmbito da Wave 2, que esta correcção não
pretende alargar. Se o D-11 institucional vier a fixar vocabulário para `transfers.status` ou se
esta correcção for formalmente adoptada no catálogo aprovado, isso deve ser feito como uma
decisão institucional separada, não como efeito colateral de uma correcção MEDIUM.

## Auditabilidade

`TransferService` nunca grava stack trace de excepção como decisão de domínio. Distingue
explicitamente:
- `TRANSFER_ALREADY_IN_PROGRESS` — decisão de domínio esperada (violação da invariante de
  concorrência), traduzida a partir do erro físico `1062` sobre `uq_transfers_membership_open`.
- `TRANSFER_INVALID_ORIGIN_DESTINATION` — decisão de domínio esperada, traduzida a partir do
  `CHECK` físico `ck_transfers_origin_destination` (`3819`).
- Qualquer outro `QueryException` (erro técnico genuíno) propaga sem tradução, para nunca ser
  confundido com uma decisão de negócio.

Não foi construída API nesta tarefa, conforme pedido.
