### Cross-process stop (Secção 14)

Reproduzido ao vivo nesta re-auditoria: `init-start --port auto` (PID 30676,
porta 33067) seguido de `stop --port 33067` como **invocação de CLI
separada**. Resultado: `STOPPED_VERIFIED`. Confirmado independentemente:
- PID 30676: `Get-Process -Id 30676` não devolve processo (terminado).
- Porta 33067: `mysqladmin ping` falha com erro 10061 (connection refused).
- Registo: `load_registered_session(33067)` devolve `None`.

I8 complementa isto via subprocess Python explícito (mesma prova, mecanismo
automatizado) — PASS.

### Foreign server stop (Secção 15)

I9: identidade da sessão adulterada após arranque genuíno → `stop()` recusa
com `FOREIGN_SERVER`, `attestation_verified=False`,
`graceful_shutdown_sent=False`, instância real permanece viva. Nenhum
shutdown foi enviado ao servidor "estrangeiro" simulado.

### 3306 guard (Secção 16)

Duplo mecanismo confirmado por leitura de código e prova ao vivo:
1. **Guard de porta** (`mysql_instance.py:203-211`): `MysqlInstance.__init__`
   levanta `ValueError` incondicionalmente se `port == 3306` — nunca um
   `assert` (que seria removido sob `-O`).
2. **Guard de atestação** (primária, para qualquer outra porta incluindo
   3307): `assert_server_attestation()` — provado ao vivo nesta re-auditoria
   directamente contra 3306/`laravel` (ver Secção "Pool attestation" acima):
   `pool_module.create_pool(3306)` → `ForeignServerError`, 0 CREATE DATABASE,
   base `laravel` inalterada.

Não se trata apenas de um port guard — a atestação por identidade do
servidor é a defesa primária para todas as portas exceto 3306 (que tem o
guard adicional dedicado). T9 confirma o guard de construção
(`ValueError` ao construir `MysqlInstance` na porta 3306).
