## 1. Scope and method

This audit maps the state present in the repository; it does not promote planned tables, diagrams or test plans to implemented capability. The evidence precedence used was: accepted ADR/canonical baseline, physical manifests and migrations, application/API/UI source, executable test source and versioned Wave attestations. Graphify was used for orientation and every material conclusion was checked against source files.

Academy was **not reaudited**. Its L7 classification is carried forward from `P0.3.5_A4_R4_final_reproducibility_attestation.md`, now versioned by the official P0.4 baseline commit `714a2e7`.

Level means the highest complete layer achieved by the vertical, not the number of tables it owns. Join, history, audit, configuration and support tables do not require independent screens. A domain is not advanced merely because another vertical reads one of its tables.

Principal evidence:

- `mepa_crm_v1.1.1.md` and ADR-0001 through ADR-0016;
- `docs/database/model_catalog.json`, data dictionary, constraints and open decisions;
- physical manifests and Gate/final reports for Waves 1–5;
- `apps/api/app`, `apps/api/routes/api.php`, `apps/web/src` and their manifests/contracts;
- API, application, database, security and E2E test sources;
- `graphify-out/graph.json` (5,485 nodes at audit time) and Graphify lessons;
- Academy R4 final reproducibility attestation.

The machine-readable resource matrix is `docs/reviews/P0.4_global_completeness_matrix.json`.

## 2. Executive conclusion

MEPA CRM has a strong physical data foundation and tested transactional services in Membership, Events, Evangelism, Discipleship and Children. It does **not** yet have a global CRM application: outside Auth and Academy there are no general HTTP routes, and the React application contains only Auth/Academy pages. Therefore physical Waves 1–4 must not be presented as user-complete modules.

Academy is the sole L7 vertical. Auth/PWA are L4 because a working browser/authentication surface exists but is bounded to Academy and lacks global administration/production closure. Five domains are L2 application-layer verticals. Eight are schema-only L1 foundations. Global Reports and mandatory Finance remain L0; Finance has a detailed approved architecture but no physical migrations or executable product layer.

| Invariant | Finding |

## 4. Domain maturity

### 4.1 Foundation and institutional structure

- **People / Families — L1.** Wave 1 physically implements Person, contacts, addresses, households and relationships. There is no general People application service, API, UI, lifecycle, report or E2E. Academy's resolver is not People CRUD.
- **Territorial Structure — L1.** The recursive tree, parent rules, locking anchor and temporal parent periods are physical. The Wave 1 Gate explicitly tracks territorial application rules for a later phase. No operational writer/read API or UI exists.
- **Physical Locations / Temples / Properties — L1.** Core locations, properties and links are physical and distinct from organizational units. The broader temple/facility/document lifecycle remains incomplete and has no application surface.
- **Documents / Files — L1.** Shared tables and versions are physical. Academy has bounded file lookup/provenance controls, but the shared upload, versioning, classification, retention and administration vertical is absent.

### 4.2 Membership, ministry and departments

- **Membership — L2.** The schema and concurrency-sensitive `MemberNumberGenerator`/`TransferService` exist with strong database tests. Approval, operator CRUD, API/UI, reports and E2E remain absent.
- **Departments / Appointments — L1.** The physical schema is substantial and correctly reuses Person, but there is no application lifecycle, API or UI. D-07 blocks institutional catalogs/seeds.
- **HR — L1 overall.** `person_employment`, education/qualification and ministerial/function assignment history exist, but they describe partial identity/ministry history rather than a complete internal employee vertical. No worker aggregate, HR lifecycle, leave/attendance decision, payroll or Finance integration exists.

### 4.3 Governance, events and credentials

- **Governance — L1.** Bodies, memberships, sessions and resolutions are physical; no application layer exists. ADR-0007 remains Proposed.
- **Events / Credentials — L2.** Wave 3 supplies physical tables and application services for invitations, credentials, access and check-in, with concurrency/domain tests. Event CRUD, HTTP/UI, reporting/export and E2E are absent. D-05 blocks production credential policy.

### 4.4 Mission and safeguarding

- **Evangelism — L2.** Wave 4 contains a tested application lifecycle and scope/temporal controls. It has no HTTP/UI/report/E2E layer.
- **Discipleship — L2.** Tracks/enrollments/progress are physical and application scope/provenance is tested. It has no HTTP/UI/report/E2E layer.
- **Children / Adolescents — L2.** Child safety, guardian/consent/custody and check-in logic have application and adversarial test evidence. The dedicated operator/API/UI vertical and privacy-safe reporting are absent.

### 4.5 Academy

- **Academy — L7.** Carried forward without reaudit from R4: 25 physical tables; complete bounded application/API/UI; 66 endpoints; 34 screens; Auth, F-06, IDOR, child safety, file provenance, application/HTTP validators, production build, accessibility/PWA and 19 E2E scenarios at four viewports. Product and evidence blockers were zero.

### 4.6 Communication, reports and administration

- **Notifications — L1.** Wave 3 has templates, audiences, campaigns and message tables. There is no delivery/outbox worker, channel adapter, retry/observability, API/UI or E2E.
- **Dashboards / Reports — L0.** The canonical model and Academy-specific dashboard exist, but there is no global reporting application/schema vertical for scoped live indicators, immutable snapshots, official closure and authorized export. `event_counts` is supporting schema, not a global BI product.
- **Administration / Configuration — L1.** Catalogs, workflows and RBAC schema exist; no controlled administration API/UI, approvals, audit coverage or E2E exists.
- **Auth / RBAC / Audit — L4.** ADR-0016 login/logout/me and browser session handling are implemented and tested. RBAC/audit enforcement is proven only for Academy and selected service layers. User/grant administration, global audit completeness, security reports and an approved MFA flow are absent.
- **PWA / Production Infrastructure — L4.** A real React/Vite PWA and production build exist, with API calls forced NetworkOnly. It is an Academy/Auth UI, not the CRM-wide PWA. The repository has only a local XAMPP deployment guide and no approved production deploy/CI/CD/monitoring/backup-restore runbook or provider qualification.

## 5. Finance — mandatory V1 assessment

Finance is **L0 and P1 mandatory**, never FUTURE. Its canonical data dictionary is unusually mature, but none of the Finance catalog tables appears in the physical Wave manifests or migrations. No Finance application, API, UI or executable product test exists.

### 5.1 Required organizational coverage

The planned ledger references the recursive `organizational_units` tree, so the design can represent Direcção Geral, Regional, Provincial, Municipal, optional Centro Geral, Centro and Congregação without separate databases. This is **design coverage only**. There is no physical account/ledger/report execution proving any of those levels.

### 5.2 Capability coverage

| Capability | Real state |
|---|---|
| Revenue, expense, cash, bank, accounts | Catalogued only |
| Supporting documents | Catalogued; shared Files schema physical, Finance linkage not physical |
| Budget and actual vs budget | Catalogued only |
| Internal transfers and approvals | Catalogued/design only |
| Reconciliation | Catalogued/design only |
| Opening/closing and periods | Catalogued only |
| Reports and export | Canonical requirement only |
| Financial audit and segregation | Canonical requirement only |

### 5.3 OWN RESULT

**NOT IMPLEMENTED.** The ledger model could derive a unit's own revenue/expense/result by unit and period, but no physical schema, query service, close/version process, API, report, export or test exists.

### 5.4 CONSOLIDATED SUBTREE RESULT

**NOT IMPLEMENTED.** The recursive tree and ledger design are compatible with subtree consolidation, but there is no executable consolidator, closing/version logic, scoped report or test.

### 5.5 Internal transfer elimination

**RULE DESIGNED; PRODUCT ABSENT.** `docs/database/04_database_constraints.md` defines SEND/RECEIVE/reversal postings and requires matched interunit receivable/payable elimination by transfer identity. `docs/database/11_financial_invariants_test_plan.md` gives the synthetic 100000/40000 invariant. These are not migrations or executable Finance tests. Until implemented and independently tested, consolidated results are unsafe because an internal transfer could be double counted.

### 5.6 Finance V1 gate

Finance cannot pass V1 until it reaches L7 with:

1. D-04 institutional accounting approval;
2. physical ledger and operational tables;
3. balanced/idempotent posting services and segregated approvals;
4. bank/cash, documents, reconciliation and periods;
5. own-unit and consolidated-subtree results;
6. mandatory internal-transfer elimination;
7. budgets, actual-vs-budget, reports and exports;
8. scoped authorization, audit, concurrency/security tests and E2E;
9. FIN-PAYROLL-01 integration.

## 6. HR and FIN-PAYROLL-01

Current physical coverage is limited to a Person's employment situation and historical ministerial/function assignments. It does not establish an internal employee, employment contract with a MEPA unit, HR attendance/leave, or payroll.

**FIN-PAYROLL-01 remains OPEN, P1, mandatory before Finance/V1 closure.** There is no schema or processing for base salary, allowances, 13th salary, leave subsidy, INSS/charges, pensions/retirement, approved third-age benefits, salary history, payroll periods, approvals or balanced ledger postings. Finance/HR/Direcções must approve scope and accounting before implementation; the roadmap must not silently reduce this to `person_employment`.

## 8. Recommended path to V1

### Recommended next vertical: People / Families

**Reason:** Person is the root identity for Membership, Departments, Events, Evangelism, Children, Academy, HR, Finance parties and portal users. Closing it first prevents every later UI/API from inventing person lookup, deduplication, address, household, document and privacy patterns. The schema is already physical, so the shortest safe step is to add the missing application/API/UI/security/evidence layers rather than start another schema-heavy domain.

**Dependencies to close with it:** ADR-0016 Auth; bounded territorial/unit lookup; shared file/document contracts; selective public IDs and F-06/IDOR; role+scope authorization; retention/legacy decisions only where they block activated operations. This vertical must allow non-members and must not issue a member number.

### Recommended sequence after it

1. **Territorial Structure** — close the recursive tree, optional Centro Geral, atomic reorganization and scope-safe reads/writes; D-12 gates real activation.
2. **Physical Locations + shared Documents/Files** — close the unit/location/property separation and reusable secure document lifecycle required by People, Events and Finance.
3. **Membership** — extend the existing L2 concurrency-safe services through approval, number issuance, transfer, API/UI, credential handoff and E2E.
4. **Finance + HR/FIN-PAYROLL-01** — mandatory V1; implement as one controlled programme after identity/tree/document foundations, proving own result, subtree consolidation and transfer elimination before UI claims.
5. **Departments / Appointments** — close Person-based appointments and history after People, tree and D-07 catalogs.
6. **Events / Credentials + Governance** — reuse Departments, locations, documents and notifications; extend the existing L2 services.
7. **Evangelism + Discipleship + Children** — promote the already-tested L2 services through API/UI/report/E2E, preserving safeguarding.
8. **Notifications** — add event/outbox delivery and operational observability, then connect completed verticals.
9. **Dashboards / Reports** — build only after source vertical semantics and Finance consolidation are stable; add snapshots, closures and exports.
10. **Administration / Configuration + global Auth/RBAC/Audit closure** — complete controlled catalog/grant administration and prove cross-domain audit/F-06/IDOR.
11. **CRM-wide PWA and production infrastructure gate** — integrate all verticals, qualify D-08, backup/restore, monitoring, security and rollout; selective offline writes remain separately gated.

This order is dependency-led. Finance is deliberately brought forward immediately after the structural prerequisites despite being L0, because it is mandatory V1 and late implementation would force reporting, HR and authorization rework. More mature L2 mission modules follow Finance because their missing work is mostly exposure/UX closure and they do not define the accounting foundation.

## 9. Final gate statement

The repository is not V1 production-ready. It is a validated data/application foundation with one complete reference vertical. The shortest safe path is to reproduce the Academy closure discipline vertically, beginning with central identity, then structural scope, mandatory Finance/Payroll, and only then global reporting and production rollout.
